## 原版没有记录时做什么

| 原代码 | 本轮核对与执行 |
| --- | --- |
| `3293a8` | 逐对象查DAT；没有命中时输出记录数组为空、atlas最大索引输出0。7份实际输入分别执行原指令 |
| `33db74` | 原新鲜场景对象构造，将两个槽的图集/参数向量清零；没有默认填另一槽的记录 |
| `33ee00` | 光照开启但记录向量为空时直接返回，且发生在清理/改写旧向量之前；对新鲜对象逐字节比较无变化 |
| `33f7b4` | 只有槽中存在非空图集指针时才加UV1_TRANSFORM，缺记录不能据此开启变换 |
| `33faa0` | 对明确非空的已加载模型指针，图集向量为空时先返回，不进入材质lightMap替换；模型指针是实验输入，不声称执行了原GPU创建 |
| 原BDAE与ut_common程序 | 原材质已有默认lightMap；没有UV1_TRANSFORM时使用原UV1，不能套虚构的图集区域 |

这些是光照附加数据的处理，不是“缺记录就删除模型”的门禁。模型读取、原创建前放行与光照绑定是不同步骤；不能把旧网页的过滤条件冒充原客户端规则。

原ARM64库仍为`77f449f2100a4717578e282bb04f1f8fff25d25c7bfa461d7d39ee49d1cb8ca4`。GhidraMCP的原工程、调用和虚表与原展开表/指令交叉核对；原so未改。完整指令及近似反编译只留本地，反编译不是原开发源码。

这里的文件存在查询、C++字符串、归档/流句柄与锁是明确环境接口；没有伪造原归档解码、Android VFS或GPU成功。归档成员存在、解压长度、CRC及最终源图SHA另外独立核对。测试还执行了只有基础包、只有较后更新包含成员及缺少部分更新包的分支。

**适用边界**：使用空名称缓存、其他文件系统提供器列表为空、原本地包集合的新鲜分支。原进程热缓存、外部提供器和后续资源修改尚未观测；这些条件不能扩大成“所有设备任何时候都必定用130”。预览资料明确记录此边界，没有把未知现场填成已恢复。
