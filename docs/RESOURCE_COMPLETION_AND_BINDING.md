## 完成结果怎样回来

模型加载的完成通知，沿用[模型任务证据](MODEL_COMPLETION_AND_BOUNDS.md)：原 worker 选候选资源，通知模型拥有者更新槽位。它说明模型任务结束，不能代替显卡资源的创建结果。

这次补查程序创建的原路径：

| 原位置 | 原代码行为 | 能说明什么 |
| --- | --- | --- |
| `0x141af90 / 0x141d368` | 比较当前线程与原对象保存的线程；指定条件下构造任务，调用 `0x117ca58`，随后调用 `0x1560858(task, 0)` 等待 | 这是所查调用分支的“提交后等待”；不能笼统说成请求后立即返回、以后再等一个异步回调 |
| 原任务表 `0x2494f20 + 0x10 → 0x142bf2c` | 重新进入原程序请求，将结果指针写回调用方输出的 `+0`，将状态写到 `+8`；旧引用按原代码释放 | 结果指针和状态分别传回，没有另造一个“GPU 一律成功”的结果 |
| `0x117ca58 → 0x1560b1c` 的直接执行分支 | 调用任务 `virtual+0x10`；之后更新完成状态，必要时发条件变量通知 | 可以关联任务体和完成通知；排队分支另经 `0x1562648`，不能把直接执行条件当所有现场线程条件 |
| `0x1560858 → 0x156093c` | 已完成时直接结束；尚未完成时走原互斥锁/条件变量等待路径 | 等待结束与程序创建成功是两件事 |

`0x150530c` 确实调用 `pthread_self` 并与原保存值比较。本轮没有查明所有线程对象的建立、队列消费者和现场线程身份，因此不自行把它命名为某个实际 GPU 线程。

上述是原代码关系的静态核查，没有在 Android 中执行任务、调用 GL 或提供成功句柄。前轮“异步完成仍缺”的范围在这里收窄；纹理驻留任务及其完整上传流程仍未闭合。

## 材质怎样变成实际绑定

原模型文件的关联仍是前轮那 12 个实例、6 个模型、7 个材质声明和 3 份效果文件。三个效果在所读两个源 profile 内均声明 `tech0` 和一个 pass；**这是文件声明，没有代选活动 profile 或证明编译成功。** 详情见[原效果与材质](EFFECT_RESOURCE_AND_MATERIAL.md)。

1. 原 `0x1474280` 先通过 `0x13ed140` 选择材质技术序号。后者受当前驱动字段和效果映射影响，不能只因文件写 `tech0` 就跳过它。
2. 若所选首个 pass 的程序 `+0xe2.bit3` 未置位，调用原 `0x13aca50` 请求编号 `0x15` 的备用材质，并替换调用方材质引用。备用请求本身也可能没有结果；本轮没有补一个颜色或外观。
3. 如果存在 transform feedback 输出对象，继续比较输出类型、语义和交错方式；不匹配时记录原诊断并返回 0，拒绝本次材质切换。**原 mesh 调用者 `0x113011c` 的两处调用未用这个返回值拦截后续绘制**，不能把这个 0 扩大成“整块地图不画”。
4. 普通绑定走 `0x1473cb8 → 0x1473fc8`，把当前材质和技术序号写入驱动 `+0x330 / +0x327`。GLES 的 `virtual+0x260 → 0x1424a7c` 取首个 pass；程序变化时，经 `0x1411fe4 → 0x1411224` 调用 `glUseProgram`。
5. `0x1437070` 处理后续 pass 的程序和状态切换，接着 `0x14112d8 / 0x141538c` 整理并提交参数。普通材质参数通过 `0x1413db0` 消费原参数映射；uniform block 路径可调用 `glBindBufferRange`。

程序绑定并非拿指针就结束。`0x1411224` 检查程序标志；相应条件下还会再次编译阶段、链接程序，然后使用程序 ID。原空程序或未就绪分支传入 `glUseProgram(0)`。原代码未在这里返回一个可以证明画面正确的成功值，不能把“调用过绑定”当成有效着色器已生效。

## 贴图与顶点还有各自的检查

`0x1413db0` 的纹理参数分支检查空引用和原状态位，需要时调用原 `0x1445120` 取得后备资源。原代码内确有 `glitch_texture_not_found` 等命名；本轮只记录原处理，未猜测其显示样式。

随后 `0x14147c8` 先经 `0x1443b98` 检查/请求纹理驻留，再按原参数标志分流。普通采样走 `0x1431ee8`：核对槽位范围、已有绑定和脏状态，需要时 `glActiveTexture / glBindTexture`，或请求原加载/上传处理。另一路 `0x1432c0c` 检查格式和槽位，绑定 image texture；不把它混作普通采样贴图。

**所查采样调用者没有把这两个绑定函数的返回值汇总成总的绘制开关。** 槽位检查返回失败不等于原引擎一定停止这次 draw；实际绑定、加载完成状态和 GL 错误仍需现场结果。

顶点输入由 `0x14118f8` 对照程序属性与几何数据：已有流设置 `glVertexAttribPointer`，部分缺失输入走转换，另一些走 `glVertexAttrib4f` 默认值，并同步启用/关闭属性数组。它的返回字节用于实例属性相关的绘制方式选择。原 `0x1424474` 对这个返回值的处理**不是“假则跳过 draw”**，不能误记成顶点完整性总检查。

## 哪些确实会挡住本次提交

| 原位置和条件 | 所查分支结果 |
| --- | --- |
| `0x315d18` 的部件绑定对象为空 | 直接返回，不发出该入口的驱动调用 |
| `0x1477984` 的几何数量为 0 | 直接返回 |
| `0x1477984` 的输出对象非空，且几何类型不匹配或含该分支禁止的索引引用 | 直接返回；这里只说明原比较，不扩展解释全部输出用途 |
| `0x1478180` 的对应能力位未开、实例数量为 0、替代模式开启或几何数量为 0 | 此变体入口直接返回 |
| `0x1424474` 的当前技术 pass 数量为 0 | 不进入 pass 循环，不到该循环内的 GL draw |

普通分支允许时，经原 `virtual+0x238 → 0x1424474`，逐 pass 提交到 `0x143ab50 / 0x143ad38`。这前面仍有[原场景与裁剪](MESH_AND_SCENE.md)、[地形区块状态](GHIDRA_MCP_AND_TERRAIN_DRAW.md)、[绘制目标与 GPU 创建](RENDER_READINESS.md)的条件；本轮没有把它们设成默认通过。

特别核对了原函数边界：`0x1477984` 只有 132 字节，后面紧接 `0x1477a08` 替代分支。Ghidra 反编译可能把跳转目标展开进同一段 C；本报告按原异常展开边界和指令区分，不把整段长反编译当作一个短检查函数。
