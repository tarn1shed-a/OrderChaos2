# 新手地图光照核对：部件顺序绑错图页

2026-11-12，基线 `4cdc7fd`。本轮查到并修正一处确定的网页接线错误：**原版按绘制部件顺序取附加光照，旧预览按材质表编号取。** 两个编号经常相同，不能因此视为同一个字段。

这解释了部分器械、桥、石柱和墙面的异常黑块，**还不能解释整张地图偏暗**。此前暗色采样的 `god_temple04` 只有一个部件，不受此错误影响。未增加灯光、曝光、天气亮度或自制美术。

## 原文件和代码证据

原 ARM64 库完整 SHA256：`77f449f2100a4717578e282bb04f1f8fff25d25c7bfa461d7d39ee49d1cb8ca4`。地址是此样本中的研究标签。

| 证据 | 实际核对结果 |
| --- | --- |
| 原模型 BDAE/BRES 的 geometry attachment | 材质引用列表头 `+0x14` 为数量，`+0x18` 相对表，记录步长 88；记录 `+0x10` 为本地材质表索引。不能把这个索引当列表顺序。 |
| `0x111b8c4`，片段 `0x111b9f8..0x111ba54` | 原列表按顺序查出材质；在重定位后的原 BRES 上实际执行。55 个非顺序模型的材质名字、表索引均与转换后分组对应。没有调用图形工厂。 |
| `0x113235c`、mesh vptr `0x244e410+0x58` | 将材质放到第 i 个 24 字节部件记录的 `+8`，绑定对象放到 `+16`。调用者传的是引用列表序号 i。 |
| `0x1132210/0x113222c/0x1132284`，vptr `+0x20/+0x28/+0x30` | 从同一数组取得部件数、几何 holder、材质。三个完整例程和虚表目标另加 SHA/重定位核验。 |
| `0x33faa0` | 遍历这些部件，以 i 取光照图页、UV 偏移和缩放；i 超过附加记录数量时用第 0 条。不是用材质表编号，也不是用另一个模型槽。 |
| `world/tutorial/lightmap/x_z.dat` | 重读 306 个相关摆放的槽 0 原对象记录，核对 ID、连续记录、排序键、图页和 16 字节 UV；与旧转换资料完全一致，错误在消费编号。 |

具体例子：`hum_other_ballista001` 的材质表编号是 `[0,1,2]`，原部件引用顺序为 `[2,0,1]`。部件 0 使用材质 2，但应取 DAT 第 0 条。旧预览给它第 2 条；三个部件的图页/UV 都可能错位。

本轮实际执行完整原 `0x113235c`、数量/几何/材质 getter 和 `0x33faa0` 循环，17 个真实实例的图页/UV 请求与修正规则一致。另用 `[2,0,1]`、`[1,0]`、16 部件逆序，分别配 1、2、N 条记录，验证越界回到第 0 条。

**实验边界：**场景查询提供一个明确节点，材质、几何、图页身份及高引用计数是隔离夹具；`0x342194` 只记录收到的参数，不执行，也不伪造参数写入或 GPU 成功。这是原 CPU 索引/传参核查，不是已启动 Android 原进程。

## 恢复范围

158 个场景模型、1258 条原摆放、251 块地形保持。其中 55 个模型、306 条摆放的部件顺序与材质表不同；逐项比较实际图页和 UV 后，**9 个模型、17 条摆放会改变输出**。其余常因只有一条 DAT 记录，按原回退规则取第 0 条，所以画面无需变化。

9 个模型：`hum_other_ballista001`、其 broken 版本，`hum_other_demolisher`、其 broken 版本，以及 `god_bridge_07`、`god_drain_05`、`god_square_pillars_01`、`god_wall_04`、`god_wall_19`。

新增浏览器适配只向既有绑定器提供正确的部件序号，保留材质表和绘制分组；实例独立副本处理，绑定完成后保留原材质编号和源部件序号。颜色贴图、UV 流、原图集、几何、摆放、光照/雾/后处理数值均不重写。灰度、摇动等既有材质参数仍由原有接线处理。

## 进入地图验收

隔离端口 8872、两名临时角色，不使用用户角色存档。实际进入原器械旁位置 `(-2444,139.4217377,-73)`，原 PHY 支撑对象 `610974232`。该点是验收输入，不能叫原出生点。

1280×720 的修正前后画面采用相同角色位置、俯仰 355°、朝向约 180.138°。镜头距离约 3.878，前后差约 0.000107 米，未超过一个像素的构图精度；截图另含两名重合的临时角色和不同时刻的动态草木，不能宣称逐像素原版帧匹配。

器械横梁区域 `(735,310)..(940,325)` 的平均 RGB 从约 `(16.34,13.94,15.66)` 变为 `(60.53,39.57,30.88)`，木材细节不再被错图页压黑；远处天空控制区域 RGB 完全相同。周围细微变化还受原动态草木和镜头浮点收敛影响。截图与读数只在本地忽略目录。

实际两端进入后按 A 行走、D 反向移动；两个窗口收到完全相同的位置和高度。第二段移动走到相邻较低支撑面，高度从 139.421738 变为 137.374741，均 grounded；没有宣称精确返回起点。刷新恢复后位置/高度与刷新前相同，两端无 warn/error。新增 8 项源/接线测试、既有空 DAT 8 项、光照编码 2 项和隔离游戏/双连接/存档 12 项回归通过；原资源不在 CI，依赖原资源的检查明确跳过，在本地执行。

## 文件结构及后续规律

- `tools/scene_part_lightmaps.py`：从原 BRES 引用和原 DAT 导出部件策略、对照结果；严格拒绝尚未覆盖的重复材质引用或多 mesh。
- `tools/native_part_lightmaps.py`：执行原索引和调用循环；显式标记夹具及未执行的参数/GPU边界。
- `tools/preview/source-part-lightmaps.js`：把已核对顺序接入现有材质绑定，不改变地图布局或光源。
- `tools/connect_part_lightmaps.py`：有界接线；重复接线或不匹配资料直接拒绝。
- `source-map-part-lightmaps/{manifest,policy,audit}.json`：本地转换资料，只新增引用；旧素材均逐文件 SHA 保持。

后续遇到“几何和贴图都正确但局部发黑”，应先按**原部件 → 材质引用 → 对象 DAT 槽 → 图页和 UV → shader 实际乘法**核对，不先改全局亮度。比对绑定只比较图页/UV，不能因记录自己的 ordinal 不同就宣称图片不同。

仍缺同位置的原版完整帧/实际 GPU 状态；完整材质变体、纹理 mip/过滤、环境过渡与阴影路径也不能由本轮索引修正推出。现有普通环境目标值未发现新的确定差异，保持原值；整图 1:1 光照仍未完成。

完整原图、表格、原生转储、截图、测试存档和可校验素材包均留本地，不上传 GitHub。自动任务 2 保持 PAUSED。
