# 原版地图加载后，一帧怎样送到屏幕

2026-11-10；基线 `2ffc481`。继续使用本机 GhidraMCP 读取原 ARM64 库，没有恢复网页原型、增加游戏功能或制作美术。自动任务 2 保持暂停。

**正常游戏状态下，从应用每帧入口、世界绘制、条件后处理到屏幕交换的主调用关系已经静态接上。仍未实际运行出原版新手地图画面，也未完成像素级 1:1 验收。** 原文件中有某种效果，不代表当前设备一定选择了它。

## 先用简单的话说

原版先更新游戏，再画当前世界。地形和建筑通过之前已核对的场景队列送往显卡；开启后处理时，先画到中间纹理，做模糊、HDR 等条件处理，再合成回之前的绘制目标。随后执行辅助叠加和设备附加对象的绘制回调，结束绘制，调用呈现接口。Android 根据应用状态决定在呈现接口内交换屏幕，还是回到帧循环末尾交换。

这里的“接上”指原库中的调用、对象创建、虚表和条件相互对应，不是用自写程序把若干函数名串起来。没有给未知调用补返回值，也没有执行或模拟成功的 GPU 调用。

地图文件与加载部分沿用已有证据：[原始加载](ORIGINAL_MAP_LOADING.md)、[区块加载与卸载](MAP_REQUEST_AND_STREAMING.md)、[Ghidra 总览](GHIDRA_MAP_FLOW.md)、[地形绘制](GHIDRA_MCP_AND_TERRAIN_DRAW.md)。本轮补的是它们外层的帧流程。

## 应用入口确实能到世界绘制

| 原代码位置 | 核对结果 |
| --- | --- |
| `0x14f17a8 → 0x14f1890` | Android 线程进入原帧循环；原诊断文本也称它为 `AppImpl::Run`。 |
| `0x3b8dfc / 0x14f1ef0 / 0x14f2078` | 原应用工厂先做基类初始化，再写最终应用虚表 `0x240f5e8`；平台对象保存所属应用。不能用基类虚表代替最终虚表。 |
| `0x14f1a28–0x14f1a34` | 符合循环状态条件时，调用所属应用的 `virtual+0x50`；最终虚表槽指向 `0x3ba314`。 |
| `0x3ba314 → 0x4cdf50` | 游戏应用创建根对象，保存到应用 `+0x3b8`；根构造器写入虚表 `0x24134b0` 并发布全局 `0x2528db0`。 |
| `0x3ba314 → root virtual+0x20 → 0x4d5488` | 游戏状态为 6 时走每帧处理。状态 5 的 `virtual+0x10 → 0x4d1558` 是启动步骤，不能误算成每帧入口。 |
| `0x4d5488 → root virtual+0x28 → 0x4d6538` | 根对象进入绘制调度，随后尾跳 `0x4d65b8`。 |
| `0x4d65b8 → 0x4dc648` | 开始显示帧后，调用世界绘制；之后还有两个辅助叠加阶段和设备附加对象回调，最后到 `0x32ae94`。 |

`0x4dc648` 仍有加载画面、暂停/同步、附加视图等条件。上表是正常游戏状态下的主连接，不能证明原客户端现在已进入此状态。

世界绘制调用 `0x34ed98`，再接之前核对的场景收集、裁剪、排序和节点绘制。地形经原 TerrainImpl 分支，建筑经原 mesh 节点分支进入驱动。先前的条件和资源缺口仍有效：找到这些入口不等于所有建筑、LOD、水面和阴影都成功画出。

## 后处理怎样回到原来的绘制目标

`0x4dc648` 在原全局开关允许时调用 `0x34a870` 和 `0x346148`。后者还检查后处理对象的状态位及计数，选择对象 `+0x60` 或 `+0x68` 的目标，经驱动 `virtual+0x130 → 0x147d610` 压入目标栈。**不是无条件开启 HDR。**

绘制世界后，`0x34632c` 检查开始标记，调用驱动 `virtual+0x138 → 0x147d79c` 弹出目标，再依次进入 `0x346574` 准备效果、`0x349104` 合成。通用小 pass `0x34b518` 也有自己的目标入栈/出栈。最终合成在 `0x34a260` 调用 `0x315d18`，画合成用几何。

目标改变在 `0x1477708` 提交：结束旧目标、调用新目标的 `virtual+0x20`。原默认目标槽可到 `0x1438458`；纹理目标槽可到 `0x1438f1c → 0x1434288`，后者确实调用 `glBindFramebuffer`，必要时创建并检查 framebuffer。`0x14395c8` 主要调整纹理目标的格式/朝向状态，不能单独把它标成绑定 framebuffer 的函数。

因此，能证明的是“合成回此前的目标”。此前目标的现场句柄未取得，**没有擅自把它设成 framebuffer 0**，也没有伪造目标创建或完整性检查成功。

## 对应哪些原效果文件

原工厂 `0x5557e0` 把类型 25 对应到 `PostEffect_Common`，类型 26 对应到 `PostEffect_BloomHDR`。名称来自原字符串和重定位表；原 `CustomEffects.bdae` 中确实有这两项定义。

- `PostEffect_Common` 引用 `pe_common_vs.glsl / pe_common_fs.glsl`；原准备代码通过宏组合选择缩小取样、模糊、Bloom/HDR、颜色校正等分支。
- `PostEffect_BloomHDR` 的两份源 profile 均包含 7 个技术：缩小取样、可变参数缩小取样、合成、可变参数合成、复制、横向模糊、纵向模糊；它们引用原 Bloom、HDR 和 Null 着色器。
- 原 `0x349104` 有通用处理和另一种 HDR 条件分支；`0x34bb58` 准备名为 `Bloom_RT%d` 的目标。最终采用哪个 profile、哪些宏、多少轮处理及哪些现场参数，仍未观测。

两种效果和所有引用着色器均从原包读取并核对 CRC、长度和 SHA。没有把独立 HDR 文件直接当成唯一活动着色器，也没有用手调曝光来补画面。

## 最后怎样交换屏幕

真正的结束/呈现主链为：

```text
世界绘制外层 0x4d65b8
  → 0x32ae94：结束显示帧
  → 0x147329c：结束驱动帧
  → 原条件允许时 0x14736b4
  → 驱动 virtual+0x190 → 0x1473788
  → 取原应用 0x14f40b4 → 0x14f3e28
  → 平台对象 virtual+0x18 → 0x150039c
```

这条链由原直接调用和两级真实虚表绑定核对。`0x147338c / 0x14733fc` 是三维与二维绘制状态间的切换，不能叫作屏幕交换；设备 `+0x20` 对象的回调也不能混作呈现接口。

两处 `eglSwapBuffers` 使用相反的应用 `+0x12c` 条件：

| 路径 | 原条件（另有生命周期守卫） |
| --- | --- |
| 帧循环 `0x14f1890`，调用点 `0x14f1b10` | 应用 `+0x12c == 0`。 |
| 显式呈现 `0x150039c`，调用点 `0x15003d4` | 应用 `+0x12c != 0`，传入参数必须为 0。该参数来自驱动 `+0x2e0`，不是凭空补的常数。 |

原构造器默认清零应用 `+0x12c`，但其他运行时写入和活动值没有穷尽。不能据此宣布当前设备一定走哪条路线，更不能说原版每帧交换两次。
