## 查到了什么

原 `5a11c8` 构造 `0x9a / C2GS_GetChatMenuList`。原 `World.proto` 只声明一个必需的 `uint64 creature_guid` 字段。完整原构造、长度计算、四字节长度前缀和protobuf序列化已离线执行；原始输入0、127、128、完整64位最大值均逐字节核对。连接关闭、抑制发送、底层socket不存在和网络对象未挂socket四种控制均没有发送。

这条请求传实际对象身份，**没有任务ID、阶段、菜单号或文字ID**。因此不能把发送请求当作主线已获准推进，也不能从客户端选中静态菜单64推定原回复必定包含六条占位文字。

固定原库完整`.text`的对齐直接B/BL与动态重定位加数中，目标 `5a11c8` 有三个直接调用位置：

| 原调用 | 本批核对 |
| --- | --- |
| `a03f98 → a040e0` | 根据原虚接口`+490`返回的按钮类型分派；原跳表2和15到此，参数从目标演员`+8`读取。类型0去另一条`0x21`请求，16从后续表现分支开始，不发送此请求。 |
| `9e51a8 → 9e5a80` | 上游计算出的局部计数至少2时到此，身份从目标演员`+8`读取。前面计数如何产生、距离、登记与模型资格没有在本批完整执行。 |

局部计数小于2不是整体“不许交谈”：原代码还可进入 `a03f98`，若显式按钮类型为2，仍会请求`0x9a`。第二版控制同时核对回退按钮17和2，避免把局部阈值误写成完整资格规则。原演员实际返回哪个按钮、容器何时由真实消息填入，仍是独立缺口。

31组明确输入，8项本地检查通过。完整执行 `a03f98` 的调度体及 `5a11c8` 的请求/序列化代码；虚接口的按钮返回、socket布局、演员与GUID是研究输入。两处 `9e51a8` 仅执行标出的片段，前半的查找、距离和模型判断被绕过，不作成功声明。后续 `5a7d3c` 与 `a038c8` 是记录边界，没有执行其副作用；STL预分配存储、分配/libc和发送记录为宿主接口。

控制中的GUID即使含原摆放编号2337，也只是明确构造的研究值，**不是恢复的NPC778活动身份**。源字段名、原跳表、函数SHA和原库完整SHA固定；变更原字节的负例会拒绝。公共CI没有原库时只核宿主输入边界，其余7项明确跳过，不将跳过写成原CPU通过。

早期`chat-request-controls-v1.json`漏列计数回退分支所用按钮输入，保留供审查，不作为权威结论；`v2`显式列出并交叉执行这项输入。第一次存储探针也因未提供STL追加接口而停止，保留失败，不把它算作成功执行。
