原区域 211 的天空请求与参数已核对，但当前收到的原资源和 APK 中缺少它实际请求的两份模型，因此本批没有用其它天空补画面，也没有提供声称可还原原天空的绘制模块。

缺的是这两个精确路径：

- `model/scene_whitepike_003/sky/whitepike_sky005.bdae`
- `model/scene_whitepike_003/sky/whitepike_skyhill005.bdae`

逐个查了本地全部 `.bin` 索引的完整路径和同名文件，再查 APK 文件清单，均未找到。本地实际有 16 条名字含 sky 的 BDAE 索引，但没有这两个模型。不能因为存在旧 `whi_sky001` 或 tutorial 天空，就当作原客户端会自动改用它们。

## 已有原文件和原代码依据

`tables/zones.tbl` 的区域 211 是 map7 基础区域，没有子区域。它的 `skybox`、`skybox_hill` 指向上述两个模型，原表中的反斜杠只做资源名规范化，没有改目录或文件名。

[`selection_scene_sky_probe.py`](../tools/selection_scene_sky_probe.py) 复用已核原构造器、状态机和全部 439 行原区域表的显式解析存储，重新运行原 map7 目录构建，再取真正目录里的区域 211 行：

1. 原 `0x4c6438–0x4c6510` 请求选择块实际运行，确实把这两条原路径分别交给 `0xa64d0c` / `0xa66de4`。模型创建在明确的记录边界停下；没有伪造资源指针或加载成功。
2. 原正常选角状态由状态机写成 1。原 `0x4c6510–0x4c6544` 根据这个真实状态生成 **0 毫秒**过渡时间，再实际执行 `0x4c6e04–0x4c730c` 天空目标写入。传入 setter 的 W20 是过渡时间，不是状态编号，二者没有混用。
3. 该 fresh-start 分支的真实当前天空值为：距离 `[0,33]`，近色 `[0.9686275125,0.9568628073,0.8627451658]`，远色 `[1,1,1]`，饱和度 `0`，天空/远山雾强度分别 `8/4`。这些是原表和原 CPU 结果，没有被写进现有网页环境。
4. 原 APK 默认 `ShowHillInSky=true`；“允许远山”不代表缺失的远山模型已经加载成功。
5. 原 `0xa63f40`、wrapper `0x3378c8` 和原位置消费者用源相机坐标做条件 CPU 核查：在两个显式“已加载节点”控制对象上，天空/远山按 X/Y/Z 跟随相机。这证明消费者规则，不能证明当前缺失模型存在或已经绘制。

当前原文件中确实有 `texture/whitepike_sky005.tga`、`texture/whitepike_sky005b.tga`，来源均已记录 SHA 和 CRC。但缺模型就无法读取它真正使用哪张纹理、哪个效果、哪个 technique、节点矩阵或包围盒。按名字把这两张图片贴到旧球体/远山上会引入未证实的模型组合，本批没有这样做。

此前 tutorial 的天空解析器和原相机跟随消费者可以复用为工具；tutorial 的模型、尺寸、选中材质和环境参数不能跨地图复制。当前也没有依据把区域 211 的天空色直接当成背景填色。
