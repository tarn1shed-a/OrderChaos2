# 新手地图显示前的配置、绘制目标与 GPU 条件

2026-11-10；基线 `b63ee5c`。继续通过本机 GhidraMCP 读取原库，并核对原 APK 和资源。这里列的是原路径、检查与失败处理；尚未取得原客户端的活动配置和 GPU 返回，不能据此宣布地图已正常显示。

本轮补齐了三件事：后处理开关怎样进入对象；默认目标和中间目标怎样创建、进入绘制栈；缓冲、纹理、着色器和程序在哪一步才真正请求显卡资源。**对象指针非空、初始化标记已置位，都不足以证明 GPU 创建成功。**

## 配置怎样决定绘制路径

先前已核对原配置来源选择、设备条件和“默认值后覆盖”顺序，见[配置来源](MAP_CONFIG_PHASE_MASK.md)、[设备档位](DEVICE_AND_INSTANCE_FILTERING.md)。本轮沿原 `0x3bb830` 补充实际字段消费：

| 原键 | 写入和消费 |
| --- | --- |
| `EnableRTTCreating` | 原布尔读取缺键参数为 true，写 config `+0xa6`，再经原 GOT 写全局 `0x250a8cd`。它控制此处后处理目标初始化及世界绘制的后处理分支。 |
| `RTTViewportScale` | 原浮点读取缺键参数为 1，写 config `+0x44`。原比较 `abs(scale−1) < float32(0.001)` 写 `0x25091f4`；后续用它区分完整视口和缩放视口。 |
| `EnableBloom` | 写 config `+0x48`；关闭时直接把下一项 `+0x49` 清零。 |
| `EnableBloomHDR` | 只有 Bloom 打开才读取此键并写 config `+0x49`；后处理初始化复制它到对象 `+0x19c`。 |
| `UseMsaa` | 写 config `+0x61`。本轮没有把这个布尔值直接等同于后处理创建时传入的采样数量；后者相关全局的完整生产链仍缺。 |

原 `GameOptions.json` 基线中：GPU 默认缩放为 1、Bloom 开、HDR 关；GPU_0M/0/1/2/3 等覆盖关闭 Bloom，GPU_6 覆盖打开 HDR。MEM 默认允许创建中间目标，MEM_0 覆盖关闭它。这些是**原文件声明**，没有替雷电选 GPU_6、MEM 档位或保存配置。

因此，后处理是可选路径。关闭它并不等于地图无法绘制；是否正常绘制仍取决于资源、目标和原场景条件。原应用早期还有一处写入中间目标开关的设备分支，不能只凭构造默认或一份 JSON 就断言活动值。

原布尔/浮点 getter 和参数写入入口另经 MCP 定位，但设备属性采集、保存/下载配置的实际内容及运行中的最终参数没有观测。没有把前轮在参数写入边界记录的实验升级成整个配置初始化已运行。

## 默认屏幕目标的来源已经接上

原 GLES 初始化 `0x1435330` 经驱动 `virtual+0x110 → 0x1422e2c` 创建默认目标，传入的外部 framebuffer 参数为 0。目标构造器在相应能力分支调用 `0x14f3e04(app, 0)`；该原函数的三条指令直接得到 0，写入目标 `+0x58`。

接着 `0x1472540` 通过原驱动 `virtual+0x130` 压入该目标，并写驱动 `+0x2a0` 和 `+0x2c8`。与前轮 `0x1477708 → 默认目标 virtual+0x20 → 0x1438458 → glBindFramebuffer` 相接。因此，**该初始化分支的 framebuffer 0 来自原代码**。非零传入句柄、其他屏幕/目标及后续替换不能一并改成 0。

这是比前轮“此前目标句柄来源未闭合”新增的证据。当前进程是否创建了此对象、后来是否仍选中它、EGL surface 是否有效，仍没有现场结果。

## 中间纹理和目标在哪里可能失败

`0x345c2c` 在原标记未初始化且创建开关允许时工作。它根据 HDR 字段选普通 `pe_rtt` 或 `pe_rtt_HDR`，经 `0x3446b4` 准备纹理、深度附件和目标；创建后处理几何缓冲后，在末尾写初始化位 bit29。这个末尾写入没有逐项汇总 GPU 成功结果，不能拿它当成功证明。

`0x147f0ac` 检查多重采样能力，不支持时按原日志和分支降为无多重采样，再经 `virtual+0x128 → 0x1423174` 创建目标包装对象。后者检查已有附件的像素格式与驱动格式映射；不匹配会记录“不支持的 render target pixel format”并返回空对象。原格式映射来自驱动版本、扩展和能力整理，不能从文件名或 HDR 名称猜设备支持。

目标真正绑定时，前轮的 `0x1434288` 创建/绑定 framebuffer，再经目标附件方法 `0x14390a0` 连接附件。该方法有两种资源来源：已有纹理走其原准备路径；renderbuffer 附件按原标志连接 renderbuffer，或转成纹理并调用 `0x143997c` 分配。这个转换分支不代表所有地图贴图的上传路径都已恢复。

`0x143997c` 使用 `glGenTextures`，按原能力选择 `glTexImage2D` 或 `glTexStorage2D`，检查错误；失败时删除纹理并返回 0。framebuffer 的完整性随后由 `glCheckFramebufferStatus` 检查。

**完整性错误在 `0x1434288` 中是记录诊断后继续返回句柄，并没有统一转换成空返回。** 因而“拿到目标句柄”不等于附件完整或画面正确，也不能把这处错误说成原引擎必定自动停止整帧。

## 地形和模型缓冲不在拿到指针时就算完成

原地形和模型已追到 `0x1462ff8` 请求缓冲。它检查用途和能力，部分用途会拒绝或降级，然后经 GLES 驱动 `virtual+0xf0 → 0x1422d58` 建立包装对象。该工厂只初始化对象和描述，未在这里调用 `glGenBuffers / glBufferData`。

真正显存创建在包装对象 `virtual+0x38 → 0x14373f0`。它先经原 `0x14f3e64` 检查 `eglGetCurrentContext`：没有当前 EGL context 时转到原通用处理路径，其后续调度不在本轮等效声明中。

有 context 的对应分支继续检查原用途能力位、生成 buffer ID、上传数据和检查 GL 错误；成功分支才设置对象 `+0x24` 的 bit6。错误分支执行清理、清 ID/设置失败序号。原 `0x1464334` 是客户端数据赋值与脏标记处理，不能误称它已完成显存上传。

本轮没有执行这些 GL 调用，也没有返回模拟成功的 buffer ID。原任务完成、模型句柄和缓冲包装指针必须与实际创建状态分开核对。

## 着色器还需要编译、链接及信息整理

原请求链继续为 `0x141c0c0 → 0x141af90`，按阶段进入 `0x141d368`。GLES 设备主接口的原工厂槽连接到文本着色器工厂 `0x1424d2c` 和程序工厂 `0x1424b94`；它们分别调用 `0x14368e4` 和 `0x1436534`。缓存、异步任务和预编译分支仍单独保留，下面只说明已核对的普通文本创建路径。

- 原预处理没有产生源字符串时，文本工厂返回空对象/状态 8。
- 创建 shader 后调用 `glShaderSource`，`0x1432db0` 执行 `glCompileShader` 并读取 `GL_COMPILE_STATUS`。失败取原日志，成功设置 shader 的编译位。已经编译的分支也会返回 0，不能孤立地把一次返回 0 当成编译失败。
- 原程序构造器执行 `glCreateProgram`、连接阶段并进入 `0x1432f2c`，读取 `GL_LINK_STATUS`。只有警告时继续；链接失败返回失败。
- 链接成功后还读取属性、uniform、uniform block 等信息，并调用原 `0x13cee9c` 整理；这一步返回失败也会使整个链接处理返回失败。其完整内部映射尚未恢复。
- 程序构造失败会删除 GL program 并将其 ID 清零。外层程序工厂仍可能返回非空包装对象，同时另写状态码，所以非空指针不足以证明程序可用于绘制。

原效果文件、shader 文件和宏定义与前轮一致，均有本地原字节。它们存在，不代表预处理、真实 profile 选择、编译、反射和绑定均已完成。
