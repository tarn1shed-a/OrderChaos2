## 原文件实际给了什么

`tables/way_points.tbl` 的固定 SHA256 为 `a28bbe03a7a8e0da5b3dcdb0cad641b5a783e66e7406a11223be5e0746623db9`。全表 14077 行、19 列，每行 76 字节，均为原标量字段；不是从文件长度猜格式。

map5 的 48 行按原 `first_wp_id / pre_wp_id / next_wp_id` 连成 **20 组**，本次所有组均能沿 next 到 0，没有缺失节点。这里只确认原数据的链接，不表示原客户端已经启动这些路径。4768 组有 10 个不同编号；最后两个点位置相同但编号不同，保留两行，没有按坐标去重。

| 原字段 | map5 实际值 | 不能据此声称 |
| --- | --- | --- |
| valid | 48 行均为 1 | 全部路径正在运行 |
| phasing_id | 48 行均为 0 | 当前玩家阶段已选择它们；不能混用地形/建筑的 phase 消费规则 |
| delay | 47 行为 0；3739 为 10000 | 未取得其消费调用，暂不指定时间单位或实际等待行为 |
| disappear | 47 行为 0；4529 为 1 | 对象一定已隐藏，或它是玩家出生/退场点 |

## 原代码如何取记录

| 原位置 | 已核对内容 |
| --- | --- |
| 0xc8b4a0 中的 0xc8b61c–0xc8b648 | 全局表管理器建立这一表对象，写 19 列、原表虚表 `0x242a008`，保存到管理器 `+0x38`。只固定相关原片段，不执行整个表管理器构造。 |
| 0xc99230 | 读取管理器 `+0x38`，取得同一表对象。 |
| `0x242a008 + 0x18 → 0xc9fa18` | 取记录入口。存储模式字节 `+0xf0` 非零时按 ID 搜索内存树；空表或未命中返回 0、保留输出。命中后复制完整 76 字节。模式为 0 则转交虚调用 `+0x58`，本轮只记录这个边界，不执行文件后备读取。 |

`native_waypoint_probe.py` 实际执行原 accessor 和完整内存取记录分支，逐字节核对 48 行 map5 原记录及 1 行其他地图的原记录。另测缺失 ID、空表、模式 0 的委托边界。内存树、对象、模式输入、栈和 libc memcpy 是明确的宿主夹具；不是在 Android 现场捕获了缓存状态，也没有执行路径跟随或原服脚本。

额外使用一份明确的反事实缓存副本，把 valid/map_id/phasing_id 改为 0/999/777，取记录仍照原代码完整复制。这说明**这个取表函数不负责筛选这些字段，更不决定人物出生**；后续消费者可以另有检查，不能说整个客户端都不检查它们。改动仅在隔离探针 RAM，没有写入原表、转换素材或角色存档。

## 调用者和触发条件查到了哪一步

原 SO 整段 `.text` 的对齐 B/BL 编码中，没有发现到专用 accessor `0xc99230` 的直接分支/调用。Ghidra 的该入口引用也只有元数据记录。另从表管理器的 1015 处引用做有界向前检查，没有找到紧接其后的固定 `+0x38` 取表；这不是完整的数据流分析，**不能排除动态索引、间接调用、脚本或原服务器使用它**。

原 `creature_spawns.tbl` 全表有 934 条非零 waypoint_id；map5 没有非零项，全部 48 个点也都没有与这 934 条静态引用直接匹配。因此没有静态 NPC 出生行把这 20 组路径接起来。不能把它们一概叫 NPC 巡逻，也不能反过来断定都是玩家开场路线。

原库还存在 `ActorNavWayPoint` 名称、工厂登记和值为 5 的对象类型。这次沿名称、原重定位和虚表查到了创建代码，但**没有把它和 way_points.tbl 的 48 行关联上**。同名不是关联证据；该候选分支不冒充已找到路径启动器。

现在缺的是：**谁拿到哪组路径编号、什么时候发起、对哪个角色/对象执行，以及后续是否改变位置/阶段**。本轮没有查到这条启动链。valid=1、phase=0、路径首行、位于任务附近，都不能替代它。

## 4768 组为什么仍值得追

它的首点约为 `(-2473.210,136.212,-66.209)`，距原新手任务给予者 750 的静态摆放在 X/Z 上约 6.94 个原单位；末点约为 `(-2581.950,136.050,-52.836)`，距任务 202 第一步区域中心在 X/Z 上约 4.39 个原单位。

这是**空间上的交叉线索**，支持继续沿任务起始交互查找；它没有证明走路者是玩家，没有证明接取任务就启动这条路径，也没有证明首点就是出生点。实际首入仍沿已核对的 `GS2C_EnterMap.location.position` 消费链接收三维位置；原服实际首包和任务脚本仍未获得。[既有入图证据](MAP_ENTRY_AND_FLOOR.md)与[过场落点](TUTORIAL_QUEST_CAMERA_CLUES.md)的边界保持。

下一项应只追任务起始/移动命令与路径编号的关联，尤其 4768 的实际发起者。91 份缺少 SQL 列名的原表仍保留未归类项；不要重复把静态字段有效性当启动条件，也不要回到无关渲染底层。
