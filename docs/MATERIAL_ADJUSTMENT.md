# 显示前的材质调整：条件与缺口

2026年11月9日，基线7f9faa7。本轮只查材质调整，不增加游戏功能，不继续扩展显卡系统；自动续跑保持暂停。

后续核对见[材质列表的建立与重建](MATERIAL_LIST_AND_REBUILD.md)：基础列表在模型部件读取阶段按材质名建立；本文停住的`0x33abb8`准备附加参数映射，不是基础列表建立入口。本文保留当轮执行边界，最新归因以续篇为准。

**这一步负责按状态更新材质选项。原调用方不拿它的返回值决定是否挂入场景；返回1也不代表贴图、着色程序或显卡已经准备好。** 上轮把这里称作“显示前的材质成功条件”，容易误导，现予更正。上轮确实在入口停下，没有伪造结果；缺口仍在后面的实际准备与重建。

## 这12项会用到哪些条件

| 原代码读取的条件 | 已核对的作用 | 这12项目前能确定到哪里 |
| --- | --- | --- |
| 对应槽是否有模型 | 没有模型时，这个调整方法返回0 | 六个原模型文件都有；运行时是否载入、选择哪个槽仍不能仅凭文件存在判断 |
| 当前选项是否等于物件缓存 | 相同就直接返回1，不重做材质 | 原加载回调把该缓存写成64；这个值本身不证明材质就绪 |
| 首份光照贴图指针是否非空 | 普通显示路径中，非空时加入UV1_TRANSFORM选项 | 两个槽共24份对象记录都能关联原光照图；实际贴图指针尚未观测 |
| 是否处于淡入淡出中间状态 | 追加相关材质选项，其中包括BLEND_COLOR | 原调用者按权重严格大于0且小于上限判断；ELF上限初值1000，当前权重不代选 |
| 原实例标志与配置 | 原实例标志启用、配置+0x40大于1时追加SHADOWMAP | 12个ITM记录的相关原字均为1；实际配置值未知，不能统一替它们开启阴影 |
| 模型保存的选项标记 | 匹配时，内部重载方法可以返回0而不重做；不匹配则进入准备/重建 | 这是避免重复处理的状态比较，不是显卡完成通知 |

以上是这段代码的条件，不是全部显示系统的充分条件。物件还要处于被选择、可见、接到场景中的状态；材质/贴图是否真正可用、最终裁剪与绘制是否放行仍需另证。附加资料和特殊显示路径没有穷尽，不能把普通路径扩大成所有状态。

原方法还有一个按槽记录的处理位。它在准备工作之前就置位，决定下次走首次准备还是后续重建，不能单独叫作“材质加载成功位”。内部重载返回0可能是选项已相同等分支，不统一命名为加载失败。外层方法在这些分支仍可缓存选项、返回1。

## 原文件已经核对的部分

- 六个模型共七份材质，引用三种效果文件；效果文件均有唯一的本地原包候选。
- 铁匠铺有两份材质，不能按每模型只有一份材质处理。
- `god_hammer_holder_01`使用的材质没有声明`lightMap`采样参数；其余本批材质声明了它。存在对象光照记录，不能推断所有材质都消费同一参数。
- 12项每个槽各有一条原光照记录，对应图页各有唯一候选。三个实例在槽1使用的图页索引与槽0不同，不能因模型文件回退而把两个槽的记录混在一起。
- 默认采样文件`texture/lightmap.tga`在两个原包中有同名、不同SHA的候选。本轮保留两份身份，没有替原VFS选择其中一份。
- 七份材质的原`CurrentTechnique`声明均为`tech0`，属性名指向GLES2。声明不等于观测到原设备实际选中了该技术或编译成功。

完整记录保留96份唯一读取材料的CRC/SHA，另保留同名默认贴图的两份候选身份。完整表格、贴图、原库、原指令和实验结果都在忽略目录`analysis/raw/material-admission-20261109/`，权威输出为`evidence.json`，不上传GitHub。

## 怎样核查，没有补什么

原场景树、ITM字段消费、配置条件、选项比较及宏文本生成执行了原指令。每项分别核对两个槽，明确提供两种配置、首贴图指针0/非0和淡入淡出条件，共192组**条件实验**；非0指针仅用于核对分支，不是制造已加载贴图。生成的UV1_TRANSFORM、SHADOWMAP等选项与原宏文本相符。

24次原准备路径实际进入首次准备入口并停止，没有提供任何准备、重建、着色程序或GPU的成功结果。原模型树仍有前轮明确的mesh存储适配；完整材质列表依赖的真实mesh/部件对象没有因此被补齐。C格式化与C++字符串存储是环境适配，选项和缓存逻辑没有改写成另一套游戏规则。

另外，使用明确的“模型已有相同选项标记”状态，执行原内部方法得到0，再由原外层方法返回1。这是缓存分支核对，不声称该缓存状态已在原客户端出现。单独执行原调用后的挂接片段，输入返回字0或1时行为一致；没有用一个自造成功值冒充完整材质加载。
