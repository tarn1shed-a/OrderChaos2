这些参数最终都进入原 `0x13dc85c`：检查参数编号、纹理类型和数组位置，再保存纹理引用、保留新引用并释放旧引用。不符合类型或越界时返回失败，不是把任意图片塞进任意槽。

本轮样本共核对 34 份纹理候选：28 份 ETC1 PVR2、4 份 PVRTC1 2bpp RGBA PVR2、2 份 TGA。**后缀 `.tga` 不代表里面一定是 TGA 数据。** 例如箱子、铁匠铺和神殿部分贴图的原字节有 `PVR!`；两份色板则确为 TGA。原文件保持压缩数据，没有转成 PNG 后冒充原上传输入。

这是一份样本文件清单，不是现场已经加载成功的 34 张贴图。两个同名默认光照图分别保留；具体哪些文件在原进程中生效仍未观测。

## 原版怎样读纹理

原 `0x143f5c4` 先处理名称、覆盖和缓存，再进入 `0x143fd80 / 0x143fed8` 等分支。`0x1443784` 通过原资源服务打开纹理名对应的流，处理偏移及流包装；它没有直接用我们磁盘上的解包文件替代原 VFS。

原读取分派先尝试加载器的流识别方法，再尝试文件名识别。PVR 加载器的原表 `0x2492428` 把这些方法连起来：

- `+0x20 → 0x13d7a0c`：读取 52 字节并检查头长度和 `PVR!`，因此能识别后缀为 `.tga` 的 PVR 数据。
- `+0x40 → 0x13d7d8c`：经 `0x13d7c38` 核对头、文件长度、mip 声明，形成纹理描述。原分支将文件编码 `0x36` 对应到引擎格式 `0x34`；所查 PVRTC 编码 `0x18` 对应 `0x29`，另有尺寸等限制。
- `+0x48 → 0x13d81c8`：再次验证头，建立原流读取对象，交给 `0x14654b4` 处理尺寸、层级和数据读入。直接读取分支 `0x14651cc` 用原纹理各面/层偏移定位缓冲，并比较请求字节数与实际读入字节数。

`0x14654b4` 还有尺寸调整、布局/格式转换和按层读取分支，本轮只把入口、直接读取分支及其调用关系接上，没有逐分支执行。两份 TGA 色板在本轮仅用本地文件识别取得元数据，没有把 PVR 读取结果扩大到 TGA 解码器。

本地包索引、长度、CRC、SHA 用于证明文件身份；它们不能证明原运行时挂载、覆盖顺序和流打开成功。ZIP/SPLIT 等分支虽然在原分派中存在，这 34 个样本没有 ZIP 纹理，未把它算作已验收样本。

## 加载任务和所谓“完成回调”

所查驻留入口 `0x1443b98` 判断当前纹理和已有加载状态，需要时设置原待加载位，构造任务并经 `0x11564c0` 提交。该任务的执行并非一个凭名称推测的回调：

`原任务表 0x24a4c28 + 0x10 → 0x1560ca0 → functor +0x10 → 原表 0x249df98 +0x10 → 0x14917dc → 0x14445f4`。

最后一个方法检查提供器的内存条件、选择加载器、验证头和读取数据，再按已有显存及数据状态进入 `0x144ab5c`。原通用执行方法 `0x1560b1c` 在任务体返回后更新完成状态，必要时通知等待者；这与[前轮任务完成证据](RESOURCE_COMPLETION_AND_BINDING.md)相接。

这里有两个不能省略的细节：内存不足、坏头或找不到加载器的分支会清除待加载位；但所查 worker 对加载器 `+0x48` 的数据读取返回值**没有直接判断**，后面继续依据对象状态决定更新。因此，“任务结束”或“待加载位清掉”都不是统一的成功证明。

缺少当前 EGL context 时，GLES 创建入口经 `0x13b22cc` 把更新交给另一个原任务。原表 `0x2494f98 +0x10 → 0x142e6c8` 再调用 `0x144ab5c`。该分派按原标志区分排队返回和提交后等待，没有把全部路径说成同步或异步。提供器内存/失效检查的实际对象、所有队列消费者和运行线程仍未完全核对。

本轮没有发现所查路径会在结束后统一遍历全部材质、重新给每个材质造一张图；已有证据是材质持有纹理引用，使用时请求驻留并解析到实际或后备纹理。不能把这个局部观察扩大为全引擎不存在其他通知机制。

## 什么时候真正上传，又怎样绑定

原 GLES 工厂 `virtual+0x248 → 0x1424948` 先经 `0x143af80` 验证设备支持的描述，再建立纹理包装对象；此时还没有执行 `glGenTextures`。包装对象 `virtual+0x90 → 0x143b43c` 才检查当前 EGL context、生成 ID、绑定目标和应用采样参数。

实际数据上传是 `0x1432354`，按原格式、面、层级和数据状态选择 `glTexImage* / glTexSubImage*`，压缩数据则走相应 `glCompressedTex*`。原方法设置像素存储状态并检查 `glGetError`；设备格式支持、压缩类型、mip 及目标不能由我们默认通过。

上传报错时记录原日志并设置纹理元数据 `+0x6a.bit4`。**该上传方法在写过错误位后仍可能返回 1。** 外层 `0x143b43c` 另查错误位，错误且已有 ID 时通过原 `virtual+0x98 → 0x143b9ac` 清理；后者含 `glDeleteTextures`。显存标志 `+0x6a.bit3`、数据脏位 `+0x68.bit1` 和错误位分别处理，不能合成一个自定“完成”状态。

回到绘制时，前轮已核对的 `0x1413db0 → 0x14147c8` 消费材质里的纹理引用，经 `0x1443b98` 处理驻留/后备，再到 `0x1431ee8` 核对采样槽、绑定和脏状态，调用 `glActiveTexture / glBindTexture`；对应参数用 `glUniform1i` 指向采样单元。原入口也可以触发尚未完成的数据更新。另一路 image texture 不混作普通采样贴图。
