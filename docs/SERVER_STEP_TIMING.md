# 服务端固定时点调度与实际容量

本批只修改网页服务器何时执行一步。`fixed_step_scheduler.mjs` 用单调时钟安排绝对50毫秒时点；游戏步长仍为原有 `.05`，原 `Date.now`、source timeval、随机状态、物理、动作队列和存档写入不改。

先执行原模板SHA校验和全部现有stage，再替换ticker启动与关闭两处。三种完整stage组合的逆变换与原文本逐字相同。没有复制不同体型或职业的计时循环。

一次timer回调只执行一步，短暂迟到最多在下一次事件循环补一步。持续超载时放弃调度债、不伪造tick或修改dt，也不在计算完成后额外等待50毫秒；这不能让超出CPU预算的工作自动达到20次/秒。scheduler的`inspect()`仅供调用方/测试读取标量，不向游戏UI或WS增加调试字段。

## 本地实测

相同私有素材、4MiB翻译缓存、2CPU、999997440字节硬限额、零交换。Linux/amd64镜像在本机ARM Mac的Docker中执行；不能将此吞吐率当成Railway原生x86的实测结果。

| 1 | 19.65次/秒 | 20.02次/秒 |
| 2 | 19.64次/秒 | 19.95次/秒 |
| 3 | 19.44次/秒 | 19.80次/秒 |

固定调度的双人、三人各持续180秒；4–6人各60秒。使用同一个normal HTTP/WS读取与校验核心，逐步加入HumanF、OrcF、Kartan、ElfF、MendelM、HumanM；完整当前binding/sourceMotion/F32姿势、位移、变化姿势与tick连续性均核对。控制组使用较短时长，窗口和原始数据分别保存，没有把控制组包装成同等时长验收。

上表包含独立计时观察开销。两组均无OOM/重启，但贴近内存上限且有缓存回收；raw cgroup peak有页级瞬时超额，不能称逐字节从未触限。新调度没有通过“4–6人全部20Hz”的整体压力门，也不证明长期无增长或全部种族职业组合的多人容量。该限制不能被单人/三人通过掩盖。

最终同一镜像去掉诊断覆盖后，正常浏览器HumanF战士创角、入图、W/S跑停、跳跃和刷新恢复通过。另一次无覆盖正常WS实测：双人60秒19.97次/秒、三人180秒19.80次/秒，完整姿势与tick校验通过。部署结果与线上步频另按实际记录，不能从本地结果宣称已发布。

## 剩余耗时与并行边界

请求发送、管道回包、shared-buffer完成及主线程等待由独立sidecar观察；原Native/Python、workerData、协议字段和校验文件原字节保留。`/proc`按同PID和starttime积分CPU，仅在相同稳态窗口以正常请求数摊销。

例如控制组六人整轮平均100.58ms，其中等待工作进程97.70ms；Python进程平均CPU约每正常请求15–16ms。传输外层的编码、pipe write调用和共享缓冲完成仅为亚毫秒量级，主要成本仍在Python/模拟执行通路。CPU、管道墙钟和调度可能重叠，不能相减后冒充精确“纯IPC”或“纯原算法”时长。位置内存记录也不是实际刷盘。

own8虽有各体型原生实例，但共用RNG、origin、lastTimeval与单一operation scope；同体型还共享活动actor/manager/compositor临时状态。现有pending.withMotion也明确拒绝重入。因此不能直接Promise.all或按角色复制worker。HumanF属于另一执行域，但安全重叠仍需所有权租约、采时、提交、事件顺序及关闭屏障的独立等价验证，当前不放行。

最窄后续候选是原调用前固定X/Q清零的批量宿主寄存器写入。已检查实际Unicorn2.1.4接口和C顺序，但未实现或承诺收益；PC、动态参数、SP/LR、原指令和计数守卫保持原路。不能把任意寄存器操作泛化批量。

## 人物显示帧取证

完整原绑定后context实际写入、原每模型更新计数及缓存消费已闭合；clock当前时间setter、range reset和本地队列调用也有具体原指令依据。原入站消息如何写入queue/clock、如何与本地显示交界仍未闭合。不是原动画文件被确认丢失，也不能把begin参数猜成网络补偿。

本批未添加客户端预测、姿势插值或非原版视觉补帧；没有把服务器约20Hz快照称为逐显示帧骨骼已恢复。原任务208/227边界、现有角色位置与存档保持，旧自动续跑仍暂停。
