## 原包里实际引用了什么

原 tutorial 的全部 ITM 共1258条 type2、92条 type8、4条 type15。四条 type15 都在 Z 约−64的既有室内任务路线，分别引用已接回的 `god_temple01_inside01` 和三份地下宫殿主体。旧角色 Z 约182旁的 `god_temple02` 是 type2，原摆放 ID715733128，不能套用 type15 的室内逻辑。

核对原包精确文件名后：

- 不存在 `god_temple02_inside*.bdae/.phy`。
- 四条 type15 各自生成的 `主模型名_inside.bdae` 和 `_inside.phy` 也都不存在，不能复制主模型伪造附属模型。
- 原包有 `god_temple06` 文件，但 tutorial 的 ITM 没有引用它；文件存在不等于此处应该加载。
- tutorial 的 EntityConfig 与 BdaeInstanceConfig 两份 XML 没有神殿02或 inside 替换条目。完整配置只留私有证据。

这些是本包的静态引用结论，不能排除缺失的原服动态对象、活动相位或其它消息输入。

## 原室内显示检查实际做了什么

本轮实际执行原 `0xa6337c`，而非再把它当未执行的边界。它读取当前 LocalHero 世界位置，沿已加载的原 PHY 链逐形状调用 virtual `+0x28` 做点包含检查；命中后读取形状 `+0x104` 的低两位，决定附属模型可见请求、内部状态值及是否调用场景状态接口 `0x34e454`。它本身不产生新模型路径，也不创建补充几何。

四份原 PHY 经原读取、原选择和原变换后，形状 flags 仅为 `0x40000000/0x40000800`。其中 bit30 是原变换过程设置；低两位仍为0。本轮没有给这些形状写入虚构的 inside 标志。

在明确的“初始活动 owner 为空、owner 状态为1”检查输入下：

- 旧下层测试位置、授权 cinematic7 外庭位置、此前实走的室内路线测试点，都未命中这四组形状的包含分支，没有发出场景或附属模型显示请求。
- 再用每组**原形状中心**作为独立测试输入，可以走进原命中分支；原代码仅发出附属模型可见请求，状态仍为1，没有场景状态切换。这验证了原消费者确实运行，不能据此把不存在的附属模型加载成功。

LocalHero 位置提供器、资源列表外壳、初始 owner/state 是明确的执行输入；显示请求接到记录端，没有虚构 GPU 或模型加载成功。测试点和形状中心不是出生点，也没有写到角色存档。
