## 原代码与实际执行边界

原ARM64库仍为`77f449f2100a4717578e282bb04f1f8fff25d25c7bfa461d7d39ee49d1cb8ca4`。GhidraMCP读取原工程、引用与近似反编译，函数范围另按原展开表及原指令核对，没有修改so。

| 原代码 | 本轮证明了什么 |
| --- | --- |
| `14118f8`及原常量表`1f416ac` | 源流没有Tangent/Binormal时，通用属性分支提交T=[1,0,0,1]、B=[0,1,0,1]。实际执行到GL调用记录接口；没有替模型计算切线 |
| `8fcb1c → a5a008 → 329700` | 普通相机构造关联名字为light的原节点，以[0,0,1]到[-1,1,-1]初始化方向；不是天空构造，也不使用网页自定太阳 |
| `11dd004`、`1413868`、`1414888` | 原四元数与对象空间方向上传实际执行；单位模型上传约[-0.57735,+0.57735,-0.57735]。另以原实例90°方向测试对象空间变换，平移不影响方向 |

最后一项纠正了接入前的错误假设：不能采用0x803省略BLEND_COLOR。原查找使用的`blend_color`字符串复用了一段OpenGL扩展名称的尾部；只有查清真实引用，才能认出它也是材质参数。扩展表里的序号不是shader语义，曾沿它推导的候选已撤回，未进入预览。

CPU隔离实验只证明上述原分支在明确输入下的结果：名称查询/反射、材质对象、GL记录为接口，四元数到矩阵及Web矩阵提交为标准宿主接口，没有伪造原材质创建或Android GPU成功。原renderer另一种常量缓冲属性后备、实际设备开关和后续灯方向覆盖仍未观测。

## 绘制与光照边界

原顶点32字节：位置float3@0、法线float3@12、UV0 float2@24；没有切线、副切线或UV1。原程序取T、负B、原N构成投影基，先在顶点计算视线和两种半角向量，再在片段归一化；不能改成网页任意生成的TBN或只在片段重算另一套高光。

法线与方向决定调色板的横向采样。颜色图乘环境光和漫反射，再加遮罩R控制的前后高光；blend_color乘算之后才加G控制的原RIM_LIGHT，最后混入原雾。原程序的常量边缘色是[0.87,0.87,1]。网页直接读取经SHA核对的原GLSL，只做GLES100到WebGL2的属性/纹理函数/输出名称转换，原代码不复制进Git。

**这条材质不消费lightMap。** 它虽有槽0 DAT记录，但效果没有LIGHTMAP，源流也没有UV1；因此不套DAT图集、不制造UV1。旧1219份烘焙绑定与全部环境配置字节保持。新材质只消费已核实的相机初始方向和既有选区的稳定颜色/强度；没有改场景灯光、天气、曝光或后处理。普通相机初始方向不等于观测到原进程整段生命周期的最终方向。

原数据的Y=107.612564照抄保留。模型正下方地形明显更低，网页中可见悬高；其是否还依赖未核实的支撑/状态不在本轮已证实范围，不能自行降模型、抬地面或补底座。新增模型不等于该区域的支撑和可走性已补齐。

尚未闭合：实际Android设备/程序和完整帧、后续方向覆盖与区域过渡过程、原过滤和全部mip上传、通用属性后备之外的设备分支、实例额外宏的完整生命周期。原场景可加入UV1_TRANSFORM/SHADOWMAP选项，但这份shader没有相应消费者，不据此制造光照图/阴影。这里恢复的是有边界的原模型材质显示，不宣称完整客户端绘制器或像素级1:1。
