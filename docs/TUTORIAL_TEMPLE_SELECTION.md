# 神殿实际实例：哪些选择门还依赖未知状态

本批接续 [具体面的核对](TUTORIAL_TEMPLE_SCENE.md) 和 [下层室内引用](TUTORIAL_TEMPLE_LOWER.md)，只核对其中七源模型的十条实际摆放：九条 type2、一条 type15。不重新统计整窗，也不补缺面。

**对这十条原摆放，未知原服活动 phase 不是当前源预加载选择的必需输入。** 原文件、原动态ID门、原档位查询和默认主模型请求都已实际核对；不能继续用笼统的“缺 phase”解释它们的静态面没有补齐。

## 字段名称更正

原 ITM 每条记录第56字节 `+0x38` 的低两位参与细节门；第60字节 `+0x3c` 是原动态ID门输入，不能叫地图 phase。原 `0xa619ac` 分支先检查它是否在1..999，只有范围内才查询 `0x2528e10` 提供的向量；范围外绕过这项门。原碰撞加载 `0xa61030` 也消费同一字段。

这十条记录的两个字都是 `0xffffffff`，动态ID字处于范围外。此前个别工具把第二个局部变量写成 `phase`，那是研究命名，不是原字段名或已经确认的 phase 语义；旧冻结文件未改，本轮输出使用 `dynamicIDWord0x3c`。

## 实际原执行结果

- 用原模型等级查询 `0x4cb934`，十条结果均为0；以−1为明确初值执行 EntityConfig 的原距离绑定检查，十条均保持原值，没有匹配这十条的距离/实例覆盖。这个检查初值不冒充原活动 owner 的现场值。
- 对每条记录，用原门执行4个细节输入 × 6个设备层输入 × 两组明确动态ID向量（空向量、`1/739/999`），共480项全部进入类型工厂前准入。它们不是480种真实设备状态，只是输入变化检查。
- APK 默认调用的主模型选择为 incoming slot0、requested slot0、forceSingleSlot=true；原文件名分支对七模型都只请求当前原 `.bdae`，没有改选 `_l` 或另一套模型。type15 的附属 `_inside` 请求仍单独保留，不能据此声称完整室内资源已就绪。
- 真正地图 phase 使用另一条链。当前原 `phasing_area.tbl` 没有 map5 行；对本批所有原 owner tile，以空活动ID、全部1..31活动ID分别执行原匹配，都得到 phase0。原 tutorial 包也不存在 `_1f` 或 phasing 子目录下的替代 ITM。

因此，本批没有发现“网页选错档位/动态ID/phase，从而省略神殿另一套静态部件”的证据。这个结论只适用于这份原包、APK默认请求和本批十条记录。

## 仍然未知的部分

原活动会话仍可能有异步完成、不同缓存历史、原父节点/室内状态更新、原服动态对象或后来替换的配置/表。原版首次出生点也没有因此恢复。它们不能用来自动生成另一套静态模型，更不能用缺输入为这十条已证实的源选择增加虚构条件。

工具为 `tools/tutorial_temple_scene_selection_probe.py`，测试为 `tools/tutorial_temple_scene_selection_tests.py`；3项本地原执行测试包含480门检查。无原资源/原生依赖的公开环境明确跳过原文件组。完整原记录、指令身份、档位结果和文件 SHA 只保存在 `analysis/raw/tutorial-temple-scene-20261114/seven-model-selection.json`。

本批没有游戏、存档、原图或生产改动，也没有补面候选。后续只针对可重现的具体显示差异继续取证，不扩成无限的通用渲染底层研究。
