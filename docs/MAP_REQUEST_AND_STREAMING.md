## 原版用什么决定加载范围

### 范围参数来自配置

原0x3bbcf0–0x3bbd14读取键 `TerrainTileSight`，传入缺键默认值2，写config对象+0x38。0xc4277c → 0xc4abf0 → 0xc62564的原树查找在键缺失时保留该默认参数。

0x35b1a0读取config+0x38得到R，设置：

| 原值/位置 | 原计算 | 含义范围 |
| --- | --- | --- |
| 0x2527a70 | R | 待请求区块偏移半径 |
| 0x2527a78 | 2×R+2 | 循环缓存每边槽数 |
| 0x2527a7c | (2×R+2)² | 循环缓存总槽数 |
| 0x2527a88 | (2×R+1)² | 偏移表项数 |
| 0x2527a80 | 原0x35b204生成的偏移表指针 | 中心先行、方环向外的次序 |

原包res.bin中的 `options/GO_ios.json` 确实有iPad2/iPad3的TerrainTileSight=1覆盖。这证明默认2并非唯一可配置值；这些iOS条目没有被当作Android当前配置。实际设备、当前profile和最终R仍未观测。

因此可以说“若输入R=2，原偏移生成器产生25个偏移，缓存分配36个槽”；不能说“这台模拟器始终加载5×5”，更不能把旧3×3预览范围当成原规则。

### 加载中心来自运行位置

0xa678b8选择两个原虚调用分支之一取位置，特定上下文又可由0x538d78返回值覆盖，然后在0xa679dc调用0x366ca0。加载入口及另一些显式重载路径会使用保存的+0x164位置。它不是以前网页的固定出生点。

0x366cc4–0x366d10对输入float32的X/Z做向负无穷取整，再按管理器+0x4c和+0x50之和作有符号右移。管理器构造器0x35b32c初始化这两个字为3、3；tutorial的AWLD配置也为3、3、1，但本轮没有把二者之间未闭合的全部写入/覆盖路径说成已查清。

在明确输入移位3+3时，原指令片段给出：

| 输入X/Z | 原片段结果 |
| --- | --- |
| -2752 / 128 | -43 / 2 |
| -0.01 / 63.99 | -1 / 0 |
| -64.01 / -64 | -2 / -1 |
| 64 / 64 | 1 / 1 |

负坐标不能用向零截断替代。这里的数值是显式输入的片段实验，不是实际角色位置观察。

## 区块加载、保留与建筑接续

| 阶段 | 原代码依据 | 本轮确认 |
| --- | --- | --- |
| 更新是否必要 | 0x366ca0 | 比较中心坐标、上下文+0x278，以及调用参数bit0和管理器标志；先处理pending状态，不是每帧重新读全部文件 |
| 遍历候选 | 0x35b204、0x366fd0–0x367224 | 按原偏移表加中心坐标；还会检查中心区块的原bitmask和phase候选资料。mask/phase完整生产者保留缺口 |
| 循环缓存查找 | 0x367684 | 对负坐标修正取模，按Zmod×缓存边长+Xmod定位；核对槽内真实坐标和地图上下文。槽号相同不等于同一地块 |
| 建立地形请求 | 0x367748–0x367794 | 未命中则0x35200c建立区块，放到manager+0x10的pending数组，并调用0x35a6dc |
| 地形任务入队 | 0x35a7b8–0x35a7fc | 建任务对象、绑定原vtable更新入口0x354ca0；送入原队列0x2527e58，保存任务ID至区块+0x178。队列管理器是0x3412a0 |
| 读取原文件 | 0x354ca0等，见上一份加载链 | 进入原TRN、遮罩、材质、导航等阶段，而非本项目自己拼网格 |
| pending发布 | 0x3673b0 | 对取消/完成标志逐项检查；所需条件满足时，从manager+0x10移到manager+8，清pending槽并调用0x3668dc/0x367884 |
| 建筑任务接续 | 0x367884 → 0xa5f518 → 0xa61f34 | 对区块坐标/类型检查已有对象，建立或复用建筑区块对象，关联到地形区块+0xf8，再提交建筑任务 |

地形和建筑不是两套按自选坐标独立放置的展示代码。已追到的路径中，建筑任务接在地形pending发布之后；这不等于完整原线程时序或所有其他建筑入口都已恢复。

## 原版怎样保留和卸载

0x366d88起会比较中心移动量、地图上下文和原调用标志。部分路径遍历并清理已有发布槽；选择性路径则保留满足条件的地块，不能把这两种路径混成单一距离算法。

在选择性路径的距离分支0x366e5c–0x366e80，只有两轴绝对差都不超过R+1才继续保留；严格大于才进入卸载。R=2的片段实验中，(±3,±3)通过距离条件，(4,0)/(0,-4)不通过。这个外圈用于保留判断，不代表系统会请求完整7×7，也不覆盖地图上下文、任务状态或缓存碰撞条件。

卸载入口0x3664e0并非直接清指针：

- 对已发布区块先问关联建筑对象的虚方法+0x68；原重定位指向0xa62c90。该方法设置卸载相关标志并检查任务ID与子对象状态。
- 若建筑暂未完成清理，原代码将其脱离地形父关系，转入manager+0x1938链表，之后在0x3672c0起继续轮询；不会在这一条分支立即释放全部对象。
- 对pending地形，设置区块+0x17c标志，根据+0x178任务ID查原任务队列，并调用0x3a7bcc处理取消状态。
- 0x352354还会按任务ID取消/等待，随后解除导航相关记录、释放或归还原数据/缓冲等。取消请求、任务退出、对象释放是不同阶段。

0x3412a0的入队和0x3a7bcc的取消有原锁、编号和队列状态依据；本轮没有用自写线程池或立即成功回调补成完整调度器。全部并发完成/取消竞争、主线程与渲染线程的最终释放保证仍待核查。

## 证据等级与剩余缺口

**已直接核对：** 请求缓冲写入、map_info格式/字段对应、TerrainTileSight读取/默认参数、半径与缓存尺寸计算、中心转换、原偏移生成、任务构造/入队、pending到建筑接续、距离保留和取消/延后清理分支。

**只在显式输入下验证：** 三段原ARM64片段的偏移表、中心坐标和距离分支。偏移表所需分配器被替代；完整加载/卸载过程没有执行。

**仍缺：** 消息名/opcode及完整分派，当前Android profile/R，中心虚调用对象类型与全部覆盖条件，移位字段全部写入者，phase表/中心mask的完整生产者，完整worker并发协议和原进程现场。也没有因此恢复原出生点、相机或角色物理。
