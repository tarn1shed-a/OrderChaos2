# 玩家执行资源与内存

本轮只优化宿主加载和数据保留，不改原 ARM64 指令、物理、动作队列、采样、随机状态或存档。原库、模型、动画、地形和碰撞资源字节保持；旧自动续跑暂停，Railway 未更新。

此前八体已共用一个 Python 工作进程和同一加载器，但进程内部为每体重新创建了 `NativeImage`，重复保留原库字节、ELF 解析、函数索引和导入表。人物原生预处理完成后，compositor 还保留整份转换模型 JSON，包括运行时不再读取的网格和预转换片段。

现在每个串行 RPC 所有者只创建一份经原构造器校验的 `NativeImage`。各体型仍检查自己的原输入；每个 Uc、全局数据、堆、场景、角色和 compositor 均保持独立。完整原生预处理、绑定和检查结束后，compositor 的 `data` 仅保留四个运行时 `compose_values` 消费者实际读取的 `rig.skins[*].boneNames`；已建立的原生缓冲、动作库、遮罩、轨道和绑定不动。单独加载时 `resources=None` 保留完整资料与独立 Image，供兼容及对照。

启动器和 Node 运行端从同一份 `tools/source_world_python.json` 的 `plans.latestWorld` 读取素材计划路径、大小和 SHA。打包器更新一处声明，消除手工同步两份校验值的依赖。

在同一 Linux/amd64 Docker 环境，基线和候选分别冷启动、使用独立空 QA 卷，以同一个冻结驱动和原九体注册表创建角色、认证入图并观察实际原生包。九个角色各处单独房间，同时驻留后采样，再全部关闭并观察三秒。此场景不发送移动或跳跃，不宣称九人同时移动通过。没有设置本地 CPU/RAM 上限、清空内核缓存或导入现有玩家存档。

| 九体同时驻留 | 基线 | 资源优化后 |
| --- | ---: | ---: |
| 进程 PSS 合计，含小型读取器 | 2.446 GiB | 1.880 GiB |
| 匿名内存 | 2.377 GiB | 1.810 GiB |
| 其中八体 Python 进程 PSS | 1766.1 MiB | 1193.5 MiB |
| 内核文件缓存 | 0.771 GiB | 1.578 GiB |
| cgroup `memory.current` | 3.217 GiB | 3.475 GiB |

进程 PSS 减少 607,830,016 字节（约 579.7 MiB、23.1%）。本次文件缓存更多，因此 cgroup 总用量反而增加，不能据此称 Docker 总内存下降。全部断开后三秒的 PSS 仍约 1.882 GiB，说明已准备的执行核心仍驻留。

剩余主要占用包括各体型独立的原生控制/物理与骨骼执行状态、人类女性原有独立执行分支、旧角色物理进程和 Node 资源。每个 Uc 还独立映射约 36 MiB 的原 RX 段。最早的本机共享缓冲原型未通过，已弃用；下文的 Linux 独立 MAP_PRIVATE 候选使用另一种所有权与写时复制方式，没有复用该原型或合并可写状态。

原生计算对照已完成：八体使用同一实际配置，基线关闭静态资料池、候选开启，分两个顺序进程执行 279 个原生 tick、1148 次 RPC。位置、队列、float32 骨骼结果、随机状态、采集上下文及完整内部快照逐项相同；静态 Image 实例由八份变一份。两个测试进程使用相同 Python 哈希种子，避免宿主 set 迭代顺序改变控制对象分配地址；服务配置与原生随机数未改。

辅助 RX 日志的旧实例编号器使用 `id(uc)`，临时对象释放后地址复用，导致最后一条编号 17/16 不同，旧汇总检查因此仍报失败，原报告保留。17 条实际写入的地址、长度、调用点，以及每个执行核心最终原代码字节均相同。独立修正后的 QA 编号器通过六组生命周期检查，含 17 个小型 Uc 和九次实际地址复用；未以删除游戏字段或改写快照来通过对照。

优化版已在本地 Linux 服务完成一次实际浏览器流程：新建人类男性游侠、入图绘制、点击及方向键行走、跳跃、接取 461、四次采集、两步原交回确认、领奖、刷新后重新登录入图。隔离账本保留 completed、四个已采对象及原奖励 512 经验、9 货币、5 声望和一件 20028；累计奖励未写入未知的原等级经验规则。旧 QA 两份存档在本轮对照前后逐字节相同，没有导入或修改生产存档。

上述浏览器验收覆盖一个代表体型；八体原生计算与九体驻留测量另列，未重复声称九人同时移动或完整职业战斗已经通过。九体进程 PSS 仍高于 1 GiB，未证明当前线上容量足够。本批保留为已本地验收的候选，不更新 Railway 或费用设置。

后续按实际线上约 1 GB RAM、零交换空间条件补验：同一人类女性体型的五个职业、五个新隔离角色同时在一个房间，收到各自及同伴的原 1928 字节姿势和三个自然状态帧。只有一个人类女性执行进程，未按职业复制核心。五人同时在线时进程 PSS 合计 680.9 MiB，匿名内存 660.3 MiB，文件缓存 240.9 MiB，容器总量 937.8 MiB；交换用量、OOM 和重启均为零。全部退出三秒后 PSS 仍为 681.3 MiB，说明执行核心继续保留。冷准备的首帧耗时 11.7 秒，其后四次首帧约 190–283 毫秒；没有发送移动输入，不作为动作延迟或长期并发验收。

这区分了职业数、同时在线角色数与已准备体型数：五职业共用一个体型核心的占用，不能按五份完整执行核心相加；同样也不能把本次单体型通过外推成九体型能在该上限内运行。先前本地允许交换空间的一轮另行保留，仅以本次零交换结果作为与线上容量的有界对照。

## 第二轮候选：资源校验与原代码页

资源校验原先会完整读入大型文件，并在返回普通 Uint8Array 时再复制一次；数个素材清单还重复读取相同文件。现在只需要校验的调用使用 64 KiB 流式 SHA，同一真实路径与元数据未变时复用校验收据；实际字节消费者仍获得单独拥有、偏移为零且 ArrayBuffer 大小完全一致的普通 Uint8Array。缓存不保留模型字节、JSON 或原生准备能力。替换文件、等长修改、错误摘要、逃逸符号链接和短读均有拒绝检查。打包器同样流式校验私有归档，避免一次读入约 554 MB。

Linux/amd64、4 KiB 页、Unicorn 2.1.4 和已校验的确切原库同时满足，且显式设置 `OC2_NATIVE_CODE_PAGES=1` 时，两处原 ELF 构造器改用共享文件作为原 RX 完整页的后备。每个 Uc 拥有独立 MAP_PRIVATE 映射，原生写入触发操作系统写时复制；末尾非完整页仍独立复制并保持原零填充。原地址、指令、guest 权限和重定位保持。单一 finalizer 先关闭 Uc 再释放映射，不依赖不同 Python 对象析构顺序；不支持的环境继续原复制路径。没有共享可写缓冲、权限故障回调或改写 PC。

候选 v13 重新使用同一冻结九体驱动与内存读取器、独立空 QA 卷和原注册表，执行与上轮相同的九角色认证入图、自然原生包及全部退出后三秒检查。没有移动、跳跃或任务输入，也没有设置本地内存上限或交换条件。

| 九体同时驻留 | 第一轮 v12 | 第二轮 v13 |
| --- | ---: | ---: |
| 进程 PSS 合计，含小型读取器 | 1.880 GiB | 1.178 GiB |
| 匿名内存 | 1.810 GiB | 1.103 GiB |
| 内核文件缓存 | 1.578 GiB | 1.690 GiB |
| cgroup `memory.current` | 3.475 GiB | 2.884 GiB |

两项运行端优化合计使 PSS 减少 753,123,328 字节（约 718.2 MiB、37.3%），相对原始 2.446 GiB 减少 51.8%。文件缓存仍增加 120,332,288 字节，容器总用量下降约 17.0%；不能只报 PSS 而隐去缓存。运行中实际观察到三个进程共 20 个原代码页映射使用同一个文件 inode。此结果是组合改动的实测，不将全部收益单独归给代码页。

当前九体匿名内存本身仍超过线上实际 999,997,440 字节、零交换的限制，因此未通过当前线上容量验收，不更新 Railway、费用或内存设置。两处原构造器的所有 PT_LOAD 字节已按段与原复制路径对照一致。随后同一候选镜像按八体实际配置，顺序运行关闭代码页/资料池的基线与开启候选：279 次原生更新、1148 次操作的完整结果、队列/控制内部快照、随机状态、采集上下文和输入记录严格一致；所有体型最终原 RX 字节与原文件一致。原复制初始化写入与映射路径的尾页写入不同，两份辅助写日志均完整保留，不强求初始化方法相同。

同一 v13 镜像随后在独立浏览器来源和 QA 房间完成新建人类男性游侠、实际绘制、方向键与点击移动、跳跃、接取 461、四次原对象采集、两步原交回确认及奖励领取，再刷新、登录同一角色并重新入图。只读核对隔离账本为 completed、四个不同采集对象及原奖励 512 经验、9 货币、5 声望和 20028 一件；重入后人物绘制正常且任务追踪已消失，浏览器无警告或错误。旧 v12 两份 QA 存档的摘要逐字节一致，没有挂载生产存档。此浏览器流程覆盖一个代表体型，不扩大为九人同时移动或五职业战斗已通过。

## 第三轮候选：实际选择与按需动作库

本批在同一加载器中透传已核对的实际首体型，只有它真实准备成功后才固定静态查询所属体型。空 `init {}` 保留旧默认行为；同域后续不能把 ground/sample/ray 改指其它体型。原共享世界输入逐项相同，所有演员仍使用各自的原动作、输入与姿势绑定；原随机状态的 push/pull 与真实查询使用同一所属体型。拒绝未知、非法或试图切换静态所属体型的请求时，不会从另一个闲置 VM 回写旧随机状态。

九个 source 角色的采集动作库在首次对应体型入图时，经过原字节与绑定校验、原库构造器实际完成后发布；同体型并发共用一个准备 Promise，失败可重试。现有 pending 事务在等待期间保留房间、槽位和角色占位，完成后再次核对原连接与角色代次，才执行原首姿势及提交；不增加游戏 tick 或时钟，不用 JSON 占位对象冒充 ready。旧角色没有该 source pending 接线，因此保留原 legacy-elf-female 单库预热。默认私有工厂仍兼容旧 eager 模式，当前共用入口明确选用 on-demand。

配置核查须沿实际运行 MRO：当前八体均使用 `oc2-shared-own-world-air-body-v1`，由 NormalLoader/ExistingLoader 走共用入口，不能从基类保留的 DELEGATES 文本推断当前仍逐体分派。HumanM 的原 composition binding 不直接保存派生编号和宽度；现有 `player_world_air_existing.declare_binding` 调用原构造器取得它们。验收读取同一个 `inputs.binding` 原文件并复用该函数，不另造绑定公式、填原表或打开旧配置字段。

第三轮使用同一最终 Linux 镜像、独立空 QA 卷，实际通过原注册表派生的全部 45 个选择：真实创建、认证入图、完整姿势、移动和停止；九种体型实际起跳、落地及同服务重连位置恢复；七种不同体型同房，一人退出后其余六人继续收到完整原生包。这不等于 45 人同房或全部职业战斗已经完成。浏览器另实际完成 HumanM 游侠创建、绘制、移动、跳跃、461 原文接取、四次原齿轮采集、两段原完成确认、奖励入账和刷新后同角色恢复。

原生对照在两个顺序进程使用同一配置与捕获输入，分别以旧默认体型和实际 HumanM 初始化，完成八体 279 次原更新、1148 次操作。全部游戏结果、完整 20 项演员快照与引用、队列、carrier、RNG、绑定和最终原 RX 字节一致。未经审定的严格比较仍保留失败：无演员的 ground 查询刷新不同静态所属体型，产生四处被动 VM 的 timeval 副本差异。独立审定把原报告 SHA、源码 pin、具体行/体型/路径及旧新值固定，证明查询只按原 `_push` 刷新该副本、闲置期间完整状态不变、后续原 reset 按重放输入完全收敛；其余字段仍走冻结比较器。没有改原报告、另造时钟、假同步或笼统忽略 timeval。15 项审定负例、13 项实际 init/query 接线检查和 55 项 Node 契约检查通过。此前检查器误要求 HumanM 原表直接保存派生绑定字段，失败日志与旧版本也保留；修正仅复用已有声明函数。

同一个冻结九体驻留驱动与内存读取器，在两个独立空卷顺序测量，均执行 13 个相同观察阶段；不设置基准内存上限，不清缓存、强制 GC 或发送移动/任务输入。下表为单次相同场景的进程合计 PSS（含相同观察进程），不是容器总占用：

空服减少约 24.3%，首次 HumanM 减少约 17.8%；九体全驻留本次高约 2.3%，没有宣称这部分改善。动作库和原生执行核心用过后仍驻留，按需加载改变准备时机，不能代替安全回收。原资料池、代码页和各可写 VM 状态的所有权保持原样。

线上只读核对仍为 999,997,440 字节、零交换。相同最终镜像在新空卷复现该条件，实际内存/交换与无 CPU 配额均经 cgroup 核查：前三体型创建、认证与完整姿势通过；第四种体型 MendelF 创建时原物理工作进程退出，HTTP 400，随后测试容器自然退出。Docker 同时记录 OOM 事件及 `OOMKilled=true`，重启次数为零。容量验收失败，不能把前三体通过当作全部可上线。失败报告、事件、日志及三个隔离测试角色保留；容器退出后的 cgroup 计数无法再读取，未伪填零。

顺序测试编排在无限额阶段正常停止后，一度把旧连接的 TIME_WAIT 误判成端口仍有监听；保留原失败记录，仅修正测试端口探针并证明真实监听仍会被拒绝，再用新空卷继续尚未开始的容量阶段。没有重跑或覆盖已通过的无限额结果，没有修改游戏运行代码。

本批未同步 Railway、改费用、提高线上限制或缩减选择范围。现有 QA 存档文件前后 SHA 均相同，未导入或写入生产存档，旧自动续跑未恢复。当前可继续优化的主要缺口是用过后常驻的体型执行核心；回收前仍须核清原时钟、随机状态、演员和查询生命周期，不能直接清空。
