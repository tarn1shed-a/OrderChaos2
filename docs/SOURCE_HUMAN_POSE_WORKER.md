# 人类原动画组合接入现有工作进程

2026-11-15。本批把已经核对的原双层动画组合和批量执行接到现有物理工作进程、角色快照及两个真实 WebSocket 客户端。它是可选运行接口，**正式创角、生产配置和 Railway 均未切换**，没有把人类角色标成已可正常游玩。此前两批的完整本地证据分别记在 `CHARACTER_HUMAN_QUEUE_COMPOSITION.md`、`CHARACTER_HUMAN_QUEUE_FAST.md`；原资源和完整执行输出另行保存在私有目录。

## 原资料与运行接口

`source_human_pose_worker.py` 在现有 `source_species_worker.py` 生成副本上增加可选的 `sourceHumanComposition` 配置；原 `source_physics_worker.py` 保持 SHA 检查和原字节。未配置时仍使用既有工作路径，不创建默认角色。

配置必须显式提供六份留在忽略目录的文件及各自 SHA256：原身体 BDAE、原动画 BDAE、已核身体 JSON、原属性遮罩证据、已核队列资料、完整组合绑定。原身体和动画的 SHA 还须与遮罩证据一致；人体、遮罩、属性顺序和当前实际登记的 Model1 队列须与绑定一致。遮罩文件的字节 SHA 与报告内部的规范化内容 SHA 是不同值，各自按对应语义核对，不互相代替。

载入后，工作进程直接消费该演员本帧的原队列结果，再执行原完整组合，输出 1992 字节 float32 值。没有从检查截图或录制姿势选帧，也没有新增优先级、动作别名、插值、装备、技能、种族或出生规则。原数学、查键时钟和游戏 tick 均未改。

`deploy/source_human_pose.mjs` 只将已有物理演员身份 `scope:playerId` 精确映射到已有公开 `playerId`。两者都不是原服 GUID。它检查整个包、绑定和每个有限 float32 后才放入快照。该字段是临时显示数据，不写角色存档；客户端不能靠名字或提交一份 JSON 给角色取得此字段。

完整原 Android 模型加载、整帧 context 工厂、GPU 完成、原服初始状态与战斗判定仍不在本批恢复声明内。

## 实际核查

- 通过可迁移载入器重新执行 33 个参考姿势，135 项属性、31 个蒙皮骨骼世界矩阵与原调色板均和原完整执行逐值相同。
- 两名人类演员和一名旧演员实际运行 48 tick，共 144 个物理及队列结果，与未增加姿势输出的旧工作进程逐值相同。人类各有独立姿势身份；旧演员不增加该字段。
- 实际服务器、HTTP 创角、两条 WebSocket：一人移动、一人静止时姿势不同，同一 tick 两个客户端的完整玩家快照一致。关闭、磁盘保存、重启、恢复原测试身份通过；存档没有姿势包。
- Mac 和 Linux/amd64 Docker 均完成上述原指令及联机核查。测试角色另建，未导入本地或生产存档。浏览器/GPU的当前人类地图验收尚未进行。

Linux 验收复用 `oc2-selection-groups-qa-20261115`。下列历史测量发生在代理自行设定的 2 CPU / 1 GiB 测试条件下，**该限制不是用户要求，也不是游戏或 Railway 的资源要求**。第一次同时保留新旧两个比较进程触及这个人为上限，出现一次 OOM，不能据此判断正式服务器内存不足。之后按正式服单工作进程拓扑依次重放同一完整输入，没有降低演员数或改算法。载入核对完成后释放不再使用的身体 JSON 和重复原字节，仍保留真正原生采样数据及骨骼名字；33 姿势比较保持相同。工作进程常驻读数由 716756 KiB 降至 572360 KiB，峰值由 834792 KiB 降至 756632 KiB。整个进程稳定性和长期队列分配仍未完成。

同一受限测试中的三演员 RPC 周期平均约 55.58 ms、p95 92.06 ms、最大 292.82 ms，含首次按需准备。这份读数不能直接推广到正常本机或实际 Railway 配置，也不作为用户必须接受某个资源档位的依据。原 50 ms tick 未改；正式开启前还需按实际运行环境检查两演员完整状态的稳定时耗。

用户指出不需要这个上限后，已重建同名本地测试容器、复用原测试磁盘并核对 `HostConfig.Memory=0`、`memory.max=max`；随后停止容器。Railway 和角色存档未改。之后不以 1 GiB 为上线门槛，失败记录仅保留为测试方法的历史证据。
