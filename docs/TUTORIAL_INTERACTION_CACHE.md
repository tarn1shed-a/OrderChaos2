## 写入缓存并不是所有更新的必经路径

原 `a42690(manager, info)` 先在32字节条目的待创建队列里找同GUID、kind6的记录。没有匹配就返回；不能单凭对象暂时不存在就缓存任意消息。

匹配后，它按GUID查 `manager+30` 处的树：已有缓存时，用原 protobuf `CopyFrom` 替换内容；没有时，构造一份独立消息副本，再插入树中。新消息不会累加成同GUID的多条任务记录。

但当前没有找到这段写入的实际调用入口。Ghidra已识别引用只有展开元数据；对完整原 `.text` 的对齐立即数 B/BL，以及 `.rela.dyn` 中指向完整函数范围的记录独立盘点，也未新增入口。该范围不含跨模块、间接寄存器或动态函数地址构造，不能断言它永远不可达。

已核的 `0x22 → a403e8` 入口则直接按GUID找对象并调用 `a4052c`，没有在该完整函数中调用上述缓存写者。不能因为缓存方法存在，就给正式客户端接上一个自行设计的“对象没好就自动缓存重发”流程。

## 哪时尝试应用缓存

原 `a430d0` 消费队列的kind6对象创建分支，先调用 `a3700c` 创建对象，再以同GUID调用 `a42e14` 尝试应用缓存。原 `5399f8` 和 `53b308` 两个调用位置分别传该队列函数第三参数0和1，随后都调用 `a312f4` 刷新对象表现；没有从这两个值自行推导新的网页计时策略。

`a42e14` 按GUID取对象和缓存，交给既有原 `a4052c`：

| 原消费者的条件 | 对该条缓存的实际处理 |
| --- | --- |
| 找不到对象、GUID不符、对象 `+c63` 非0 | 返回0，保留缓存 |
| 原应用函数返回低位1 | 析构缓存消息、移除树节点、减缓存数 |

`+c63` 仍只按原字节门描述，没有将其命名为完整的模型/GPU就绪状态。应用失败后保留记录，也不等于原程序会每帧无条件重试；目前定位到的直接应用调用仍在上述对象创建分支中。

原 `a3fd00` 可单独按GUID清一条交互缓存；`a3f6ec` 释放待创建记录与三组缓存并重置容器。`a3f940` 的清理与待创建条目命中有关，不能泛化为所有情况下都清空某GUID。

## 原指令实际核对

新增研究工具 `tools/tutorial_interaction_cache_probe.py`，6组对照实际执行原复制、查找、替换、门判断和清理：

- 空消息、非kind6和不匹配GUID均不入缓存。
- 原消息及交互条目被独立复制，修改研究输入不影响已缓存内容。
- 同GUID再次写入保留一条消息对象，内容替换为新输入。
- 对象不存在或 `+c63` 置位时，明确调用应用函数仍保留缓存。
- 将研究字节门清零后，再次明确调用应用函数，原代码复制交互条目并删除缓存。
- 单GUID清理及整体清理均按原代码移除缓存。

这些是**显式实验输入**：待创建队列、对象登记树、内存中的protobuf字段、最小对象及属性双份编码，不是原会话、原NPC创建或收到的服务器消息。原protobuf构造/复制代码确实执行；源重复字段的存储由实验提供，没有运行原网络解析器。

分配、libc和释放为具名接口，释放动作被记录，实验arena不回收。仅对象虚槽98的void表现通知被记录；未提供资格函数返回true、任务批准或奖励。对照使用属性值0，因此不覆盖原0x40a非任务交互分支、完整聊天菜单或所有对象类型。工具记录原函数入口次数，不把研究程序自身判断称为原代码执行。
