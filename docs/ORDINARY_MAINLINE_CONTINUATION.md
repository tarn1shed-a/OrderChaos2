## 208的实际缺口

208的原标题、接取正文、交谈目标和完成正文存在；原接取人物是NPC8，交回人物是NPC778。原目标表只有一条 `obj_idx=1/type6/value0`。逻辑443却引用不存在的 `obj_idx=2` 和对象202；本轮明确记录为孤立引用，没有据此加第二个目标。

NPC778的原推荐菜单是64，静态连接为：

`64 → option200000132 → 65 → option200000133 → 66 → option200000134`

最后一个选项的脚本名与逻辑444的 `quest208_chat64_option134` 相同，逻辑471的entry也指向该选项。这些是实际原表连接，不只是从脚本名猜的关系。但是三段菜单与三个选项所引用的原中文字面值均为 `test`。英文与默认文字表的同ID也为 `test`；任务正文没有被改写成缺失对白。

文字表绑定已从原客户端核对：原菜单接收 `58b678` 后由 `3e65b8/3e44f8 → e861c8 → c999f8` 查询管理器 `+0x800`；原构造器 `c92190` 放入的表对象使用vptr `243e6d8`，加载函数 `e68f04` 实际组装 `String_Chat_Menu_<language>.tbl`。因此不是按相似文件名选错表。原服收到的菜单和文字ID仍可能不同于静态推荐，本轮没有得到真实会话输入，不能断言原玩家必定见过这六个 `test`。

原ChatMenu的选项点击调用 `ChatMenu_SendSelectedOption → 6a984c → 5a106c`，组装原 `0x99` 请求；没有把 `link_menu` 当成已验证的浏览器本地翻页规则。未恢复这些原脚本的副作用，也未把“选中最后选项”直接认作已收到原任务完成回执。

## 后续任务不能仅凭“脚本为空”放行

447自己的quest.script为空，但箱子原型202实际有 `quest208_obj202_ai`；原Type6、技能364、图标和四个烧箱子目标都在。技能364的事件还引用施法开始、取消和释放脚本。不能拿旧的临时技能240替代364，也不能用一按即消失的采集流程冒充烧箱子。

209含多步任务和额外对话/脚本引用。210的原目标较简单，但前置是209；不能为了演示直接跳过前置发任务。

原 `quest_objective_logic` 的 `ca7e3c/ca835c` 是记录读写，字段模式为 `uuuuuusuiu`，不是任务执行器。对本轮具名查行函数 `ca6858/ca6b4c` 的Ghidra静态引用只找到了表和虚函数资料，未找到直接游戏调用。这个有限结果不证明全客户端或间接调用中没有消费者，也不能补出原判定规则。
