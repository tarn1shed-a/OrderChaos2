## 位置从哪里来

这次把之前未命名的消息与原库里的消息定义对应上了：

| 原文件/原代码 | 本轮确认 |
| --- | --- |
| 原 SO 内 GameServerOld.proto 描述，0x2028b48 / 64615 字节 | 共 475 个消息；第 13 个为 GS2C_ObjectLocation，第 14 个为 GS2C_EnterMap。前者带 map_id、position、direction、可选 speed；后者的必需 location 指向前者。position 的类型是 CxGS_Vec3。完整描述仍只留本地。 |
| 0x1bb0b60 构造器、原 vtable 0x24e1450、元数据入口 0x1bb1948、0x1b856d4 初始化 | 元数据对应上述第 14 个消息；因此可以把 0xa34f28 使用的解析对象命名为 GS2C_EnterMap。不能据此猜 opcode 或称收到过真实原服包。 |
| 0xa34f28；0xa35654 起的位置/方向读取与虚调用 +0x448 | 读取 location.position 的三个字，作为角色重定位的位置参数。不是从 map_info.enter_pos 取三个默认值。 |
| Hero 原构造器 0x9ec7c8；vtable 0x24228a8 | +0x448→0xa0e3ac→0x9037d4；后者调用 +0x68→0xa0902c。原 setter 将三个坐标同时写入当前位置 +0x118 和待处理位置 +0x1ac，保留输入高度。 |
| 0xa358c0–0xa35900 | 从主角色原 +0x70 getter 取位置，完整保存到上下文 +0x164/+0x168/+0x16c，并设置重载标记 +0xb9。本轮实际执行 getter 与整段复制。 |
| 0x53966c–0x53967c→0x366ca0 | 保存位置交给区块加载；地块中心仅按 X/Z 换算，高度并未因此变成地形采样值。 |

明确边界：setter、中心保存和初始支撑是本轮执行的原 CPU 路径；消息解析到重定位的关联有反汇编/原元数据证据，但没有执行完整网络分派，也没有伪造成功的原服回复。

## 楼层怎样选

原 Hero vtable +0x128 指向 **0x90c348**。0x9e1970 的特定分支在待处理标记 +0x58c 非零且地块可用时清标记并调用它；不是不加条件地每次入图都强制执行。

0x90c348 还要求角色类型/标记通过，以及上下文加载状态对象 +0x58 为 1、+0x40 为 4。两个数字是原字段条件，不编造原枚举名。本轮显式提供这些状态作为夹具，没有运行完整加载状态机。

条件通过后，以 **待处理 Y + 0.5** 调用原 **0xa87750→0x363b9c**。后者先取原地形高度，再从这个高度上限向下查询原建筑 PHY 支撑。它不按建筑名字指定“第几楼”，也不无条件选整列最高表面。

该函数缓存支撑到 +0xbfc，置 +0xc00，并更新待处理位置；这一步不直接改当前位置。水状态和一个 +0x1e8 对象的 +0x70 标记还可保留原待处理高度，不能把它简化成“任何位置都贴地”。该对象完整生命周期仍未闭合。

在截图区域同一 X/Z（-2611.41015625，185.84120178222656），实际执行原 setter、中心保存和完整 0x90c348 得到：

| 显式输入高度 | 状态条件 | 原待处理高度 |
| --- | --- | --- |
| 132.349991 | 1 / 4 | 132.349991，下层 |
| 150 | 1 / 4 | 132.349991，下层 |
| 172.366898 | 1 / 4 | 172.366898，上层 |
| 196 | 1 / 4 | 172.366898，上层 |
| 172.366898 | 0 / 4 或 1 / 3 | 保留输入，不产生支撑缓存 |
| 196 | 1 / 4，显式 +0x1e8/+0x70 保留分支 | 待处理高度仍为 196，缓存支撑为 172.366898 |

这些位置都是检查输入，**不是恢复出的原出生点**。场景容器、静态驻留集合、角色身份和状态由宿主提供；原 PHY 读取/变换/查询、setter、位置保存与初始支撑 CPU 执行原指令。干燥神殿夹具不冒称完整游泳、动态对象或 Android 现场。

## 首入坐标的缺口

原 map_info 的 map5 指向 world/tutorial.wld，enter_pos_x/y/z/o 全 0。player_spawn 六条记录只有 map1/3；不是 map5 的出生表。本轮另外重读：

| 原表 | 总记录 | map5 记录 |
| --- | ---: | ---: |
| map_transfer_point_info | 14 | 0 |
| teleport_spot | 251 | 0 |
| area_trigger | 404 | 1 |
| quest_map_exit | 45 | 0 |
| bot_map_factory | 30 | 0 |

唯一 map5 触发区为 399，引用 tutorial_areaTrigger399。它是触发区记录，未找到将它用作首入位置的原调用；不能拿它、NPC 坐标或屋顶测试点代替出生点。已重读的这些表未提供所需值，不等于证明整个客户端绝无其他位置来源。

当前预览的新角色仍使用旧网页 world.spawn=(900,360)，另有本地并发角色偏移和 JSON 存档恢复；这些是早期自写适配。没有原服消息里的 map5 三维位置及对应活动状态，不能决定当前下层视角就是原开局，也不能把角色统一抬高 40 米宣称修好神殿。

接回正式入图前还缺：真实首入 GS2C_EnterMap.location，或可与该消息消费链交叉核对的原服脚本/记录；完整待处理加载发布和特殊保留条件的生命周期。浏览器恢复本地存档的代码不冒称原入图流程。本轮只把原 CPU 已确定的两层结果送入独立预览夹具做核对，没有将夹具包装成原版开局。

[原执行探针](../tools/native_map_entry_probe.py)、[证据重放](../tools/map_entry_evidence.py)与[检查](../tools/map_entry_evidence_tests.py)固定原 SHA、函数身份和 Hero 槽关系。6 项检查通过；无源资料的 CI 执行 2 项描述边界检查，4 项原资料检查明确跳过。

独立 8877/独立存档中，两名测试角色分别使用原 CPU 得到的上下层支撑。实际按键短走、停步、两端位置/高度一致、上层刷新恢复通过；上层累计 X/Z 位移约 0.96/-1.44，下层 X 位移约 -1.68，均未换层。浏览器无 warn/error。仅是短路线检查，不证明上下层连通、整张地图可玩或原出生正确。上层截图也保留屋顶边缘/远处未完整呈现，不能把此观察点称原开局视角。
